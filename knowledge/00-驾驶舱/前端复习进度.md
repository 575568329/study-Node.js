8. ✅ Q8 重排重绘：渲染管线 6 步 + reflow/repaint/composite 三档开销 + 布局抖动
9. ✅ Q9 CSS 单位：em 复利累乘 vs rem 稳定 + vw/vh + % 高度陷阱 + vh 移动端
10. ✅ Q10 1px 边框：DPR + CSS像素vs物理像素 + 伪元素 scaleY 压缩方案

**关键收获**：
- 渲染管线：DOM/CSSOM → Render 树 → **Layout(reflow) → Paint(repaint) → Composite**
- 三档性能开销：几何属性(reflow 最贵) > 外观属性(只 repaint) > transform/opacity(只合成，GPU 最便宜)
- transform 便宜的原因：提升为 GPU 图层"挪贴纸"，坑不动+像素不重画，跳过 ④⑤（跳过是因、快是果）
- 布局抖动（强制同步布局）：读几何值(offsetWidth 等)会逼浏览器立即 reflow → **读写分离**修复
- em 相对父级会逐层累乘（复利失控）；rem 相对根 `<html>`（非 body）永远一把尺
- vw 认视口宽 / vh 认视口高；% 高度需父级有确定高度；vh 移动端跟地址栏打架 → dvh
- 1px 问题根源：DPR≥2 时 1 CSS px = 多个物理像素，细线做不出 → 伪元素 + scaleY(1/DPR)

**错题本**（概念模糊 / 因果倒置，复习重点）：
- 🔴 **判断依据错**：说"background-color 不 reflow 是因为 DOM 没改" → 正确依据是"看改的属性动没动布局"（改 width 不动 DOM 也 reflow）
- 🔴 **因果倒置**：说"transform 性能好所以跳过步骤" → 反了，"跳过 layout/paint 是因，性能好是果"
- 🔴 **概念模糊**：rem 说成"相对 body" → 是根元素 `<html>`（移动端适配设 html 字号的原因）
- 🟡 **计算失误**：100vh 在 1200×800 视口算成 600（抄了宽度）→ vh 认高，应 800
- 🟡 **术语不精**：画线的 `::after` 说成"伪类" → 是伪元素（造元素）；伪类是选状态/位置

**里程碑**：🎉 **CSS 10/10 全部收官**，复习线 JS/TS → Vue3 → CSS 三块完成，下一站 Node.js

  - 顶层 setTimeout(0) vs setImmediate → **不固定**（看 1ms 到没到期）
  - I/O 回调里 setImmediate **必赢** setTimeout（poll 之后紧接 check，同轮）
- await 的同步性：`await async2()` 先同步执行 async2 函数体，再暂停当前函数；await 后的代码 = `.then`，是微任务
- 综合执行顺序题方法：分三类排队（同步 → 微任务[nextTick 先] → 宏任务），同步按代码书写顺序

**错题本**（概念模糊 / 结论过度推广，复习重点）：
- 🔴 **结论过度推广**：把"I/O 回调里 setImmediate 必赢"推广到"所有场景 setImmediate 都比 setTimeout 快" → 只在 I/O 回调内成立，顶层不固定。判断依据是"是否同轮相邻阶段"
- 🔴 **await 同步性**：综合题把 B 排在 C 前（答 `...A B...`）→ 应 `A C ... B`。await 先同步执行 async2 体（打印 C），再暂停注册 B 为微任务

- 🟡 **综合时序**：readFile 回调与顶层 setTimeout/setImmediate 的先后判断混（I/O 比定时器慢，顶层通常先跑；且 readFile 回调内注册的 4 是本轮 check、7 是下轮 timers，4 必在 7 前）

### ✅ Node 原生 http 模块

**`req` 是 Readable 流，`req.body` 不存在**：
- 回调在**请求头解析完**就触发，body 还在网络上飘
- 回调时能拿到：`req.method` / `req.url`（只有路径+query）/ `req.headers`（key 全小写）
- **拿不到 `req.body`**——那是 `express.json()` 后来挂上去的
- 设计原因：body 可能 2GB（文件上传），不可能等全到齐才回调 → 做成流让你自己消费

**手动收 body 的正确写法**：
```js
const chunks = []
req.on('data', chunk => chunks.push(chunk))
req.on('end', () => {
  const body = Buffer.concat(chunks).toString('utf8')
})
```
⚠️ **生产 bug**：别写 `body += chunk`——中文 UTF-8 占 3 字节，正好切在 chunk 边界会乱码。必须攒 Buffer 最后一次性解码。

**`res` 是 Writable 流**：
- `res.writeHead()` 必须在 `res.end()` 之前（HTTP 协议规定头先发，写完 body 再改头报 `ERR_HTTP_HEADERS_SENT`）
- `charset=utf-8` 别省，不写中文可能乱码
- **不调 `res.end()` = 请求永久挂起**（浏览器转圈到超时）→ 每个 if 分支后加 `return` 防漏

**Express 到底封装了什么**：
| | 原生 http | Express | Spring MVC |
|---|---|---|---|
| 路由 | `if (req.url === ...)` | `app.post('/x')` | `@PostMapping("/x")` |
| 取 body | 手动收流 | `express.json()` | `@RequestBody` |
| 返 JSON | 手动 stringify | `res.json()` | `@ResponseBody` |

三边同结构：**底层都是流，上层框架 buffer + 反序列化**。

**实战代码**：`projects/nodejs/01-express-demo/http-test.js`（POST 路由 + 流式收 body + 400/404 处理 + error 监听）

### ✅ cluster 多进程（吃满多核）

**核心机制**：只有主进程 `listen`，worker 不 listen
- 主进程收连接 → 通过 IPC 把 socket 句柄传给 worker
- 从 OS 看 3000 端口始终只被 1 个进程占用 → 不冲突
- **cluster 劫持了 `listen`**：worker 里调 `listen` 不真绑端口，只发消息说"我准备好了"

**关键限制：worker 之间不共享内存**
- `let count = 0` 在 4 个 worker 里是 4 份独立变量 → 数据全乱
- 必须外置到 Redis：Session / 缓存 / 计数器 / 限流 / WebSocket 广播
- **回扣 JWT**：无状态所以任何 worker 都能独立验签——07-29 学的"Session 跨服务器问题"在 cluster 里就已出现，不用等多机

**生产用 PM2 不手写 cluster**：
- `pm2 start app.js -i max`（按核数起）/ `pm2 reload`（零停机滚动重启）

**对比 Java 并发哲学**：
| | Node | Java (Spring Boot) |
|---|---|---|
| 模型 | 单线程事件循环 + 多进程 | 多线程（Tomcat 默认 200 线程）|
| 吃满多核 | 起 N 进程（cluster/PM2）| JVM 内多线程天然用 |
| 状态共享 | ❌ 进程隔离，必须外置 | ✅ 内存共享（但要加锁）|
| 代价 | 内存 ×N | 并发安全问题（锁/竞态/死锁）|

**根本分歧**：Node 用"进程隔离"换"不用写锁"（单线程天然无竞态），代价是共享状态必须外置。

```js
} catch (err) {

  throw err
} finally {
  conn.release()
}
```

2. **流式响应本质**
   - `res.write()` 边缘触发立即发送，不等 `res.end()`
   - 区别于 `await res.json()` 全量缓冲后解析
   - AI 应用流式输出的技术基础

3. **EventSource 生命周期**
   - 服务端 `res.end()` / 网络断开 → 触发客户端 `onerror` → 自动重连（默认 3 秒）
   - 客户端 `es.close()` → 设置 `readyState = CLOSED` → **不触发 `onerror`、阻止重连**
   - 约定：服务端发 `[DONE]` 标记 → 客户端收到后调 `close()` 优雅关闭

4. **技术选型洞察**
   - SSE vs WebSocket：SSE 是单向低成本方案（无协议升级、自动重连、标准 HTTP）
   - AI 对话场景：客户端不回推数据 → WebSocket 双向通信是过度设计
   - 成本对比：SSE 够用就不付 WebSocket 的协议升级和心跳维护成本

5. **生产三大坑**
   - **Nginx 缓冲**：`proxy_buffering off` 或后端 `X-Accel-Buffering: no`（默认攒够 4KB 才转发，几十字节的消息会卡十几秒）
   - **连接泄漏**：`req.on('close')` 监听客户端断开，`clearInterval(timer)` 清理资源
   - **CORS**：`file://` 协议打开 HTML，origin 是 `null`，需要 `Access-Control-Allow-Origin: *`

6. **排查顺序**（面试亮点）
   - 第一步：抓包/DevTools Network 对比服务器发送时间戳 vs 浏览器接收时间戳
   - 第二步：检查 Nginx/网关配置 `proxy_buffering` / `X-Accel-Buffering`
   - 第三步：代码层（`res.write()` 时机、`\n\n` 终止符）

### 理解盲区修正

3. **误以为 `es.close()` 会触发 `onerror`**

   - 纠正：只有服务端断开（`res.end()` / 网络故障）触发 `onerror` + 自动重连；客户端 `es.close()` 设置 `readyState = CLOSED`，不触发 `onerror`，阻止重连

### 过关题目（③ 心智模型，3 问 + 实验验证）

**Q1 React 不监听，它"重跑整个函数"**：
- 学生答：方向对（要用函数改），但"react 通过函数监听" ❌ **这是最关键误解**
- 纠正：**React 根本不监听**。`setCount(1)` 不是"改变量"，是"通知 React 重新调用整个组件函数"
- **核心认知**：重渲染 = 组件函数被 React 从头重跑一遍（不是精准更新局部变量）
- 对比 Vue：Vue 用 Proxy 监听自动追踪，React 是"你喊一声(setState)，我把整个函数重跑"

**Q2 不可变(Immutable)铁律**：
- 代码题：`list.push(4)` 界面会不会变？学生答"不会" ✅ 对，但理由"没执行" ❌ 反了
- **真正原因（两层）**：
  1. 没调 `setState` → React 不知道要更新（不监听的直接后果）
  2. 即使加 setState，`list.push(4)` 改原数组、引用不变 → React 认为"没变"
- **铁律**：改 state 永远**造新的**（`[...arr, 4]` / `{...obj}`），不能原地修改（push/splice/obj.x=1）
- **根因**：React 判断"变没变"靠**比引用**（旧 list === 新 list?），引用不变认为没变 → 不重渲染
- 对比 Vue：Vue 的 Proxy 监听到数组变化，`push` 完全 OK；React 不行

**Q3 受控组件 vs 单向数据流**：
- 学生忘了 → 补讲：React 无双向绑定，要手动接环：`value={text}` + `onChange={e => setText(e.target.value)}`
- **为什么不给双向绑定**：信仰**单向数据流**（state → 视图，视图改数据必须显式调函数），数据怎么变的永远看得见、追得到
- Vue 的 `v-model` 也是这个环的语法糖（`:value` + `@input`），只是 Vue 包好了糖

**动手实验（MutableExperiment.tsx）**：
- 亲眼验证：点 ❌（push 改原数组）界面不动，控制台数组确实变长 → React 不监听 + 引用不变认为没变
- 点 ✅（setList 造新数组）界面跳变，把之前偷偷 push 的值一次性全显示 → setState 通知重跑
- 学生结论："**只有重新创建一个数组才会生效**" ✅ 钉死

### 过关题目（④ Hooks 全家桶，闭包陷阱 + 依赖数组 + useCallback/useMemo）

**经典闭包陷阱题（setInterval 打印旧值）**：
```jsx
useEffect(() => {
  setInterval(() => console.log(count), 1000)
}, [])  // 空依赖
// 狂点按钮到 5，控制台每秒打印什么？
```
- 学生答：Q1"不变" ✅ 对（打印 0）/ Q2"useEffect 没重新执行" ⚠️ 对一半 / Q3"count 没更新" ⚠️ 描述现象非机制
- **机制补全（闭包快照）**：
  - 每次渲染函数重跑，产生全新独立的 `count`（0,1,2,3,4,5），它们是不同渲染的**快照**
  - 第 0 次渲染：useEffect 执行，`setInterval` 回调**闭包捕获了这一次的 count=0**
  - 空依赖 `[]` → effect 一辈子只跑这一次，timer 永远是那个闭包冻住 count=0 的回调
  - 点按钮 → count 变成 1,2,5 → 函数重跑产生**新的 count**，但旧 timer 闭包还锁着第 0 次那个 count=0
  - **脱节**：界面用最新的 count(5)，setInterval 回调用第 0 次被闭包冻住的 count(0)
- **一句话**：setInterval 闭包"拍了张快照"，把第 0 次渲染的 count=0 冻住；后面 count 变 1、5 是新渲染的新变量，和快照无关
- **修法**：`useEffect(..., [count])` 诚实声明依赖 → count 变就重建 timer，新 timer 闭包捕获新 count

**依赖数组三种写法**：
| 写法 | 执行时机 | 对标 Vue |
|------|---------|---------|
| 不写 | 每次渲染后都执行 | — |
| `[]` | 只在挂载后执行一次 | `onMounted` |
| `[a,b]` | 挂载 + a/b 变化时执行 | `watch([a,b])` |
- return 的清理函数：每次 effect 重新执行前清理上一次 + 组件卸载时清理（对标 Vue onUnmounted + 更强）

**useCallback vs useMemo 推理题**：
- Q1：函数重跑时 `handleClick = () => {...}` 是同一个还是新造的？学生答"新的" ✅ 对（引用变了）
- Q2：count 没变但组件重渲染，`heavyCompute(count)` 会不会白算一次？学生答"会啊" ✅ 对
- Q3：推 useCallback 管函数、useMemo 管值？学生答 ✅ 全对，**用"函数重跑"成功推出来**
- **useCallback**：缓存函数本身（避免每次造新函数 → 子组件白重渲染），典型场景：传给用了 memo 的子组件的回调
- **useMemo**：缓存计算结果（避免每次都重算），典型场景：耗时计算（>50ms）
- **最容易踩的坑**：**滥用反而更慢**——简单计算、没性能问题的组件别用，缓存成本 > 计算成本；**过早优化是万恶之源**
- **2026 面试高频**："useMemo 什么时候拖累性能？"答：用在简单计算上

### 关键盲区修正（这次真懂了的点）

1. **"React 通过函数监听" → React 根本不监听**（③ 站最大误解，贯穿后续所有理解）
2. **"push 没执行" → push 确实执行了，数组确实变了**，但 React 不知道（不监听）+ 引用不变认为没变（不可变铁律）
3. **闭包陷阱的根源**：不是"effect 没重新执行"（表面），是**闭包冻住了某次渲染的快照**，后续渲染的新变量和它无关
4. **useCallback/useMemo 何时用**：不是"见函数就 useCallback"，而是**先不用，等真的遇到性能问题再加**（profiler 测出来）

### 记忆锚点（贯穿 ③④ 两站）

> 1. **重渲染 = 组件函数从头重跑一遍**（不是改局部变量）
> 2. **React 不监听数据**，靠 `setState` 通知它重跑
> 3. **改 state 要造新的**（不可变），React 靠比引用判断变没变
> 4. **闭包陷阱 = effect 回调冻住旧渲染的快照 + 空依赖让它不更新** → 解法：诚实声明依赖
> 5. **useCallback 缓存函数、useMemo 缓存值**，但别滥用（简单场景反而更慢）

  - **判断"要不要加缓存"**：看 profiler 数据权衡成本收益，AI 生成的代码常满屏 useCallback（过度优化）
  - **排查闭包陷阱 bug**：需要理解"快照"机制，AI 能修代码但讲不清根因

- 补：cluster 多进程（内存隔离，共享外置 Redis）、worker_threads 多线程（可共享内存 SharedArrayBuffer）；99% 场景用 cluster 够

### 过关题目（⑥ 站，3 问）

**Q1 受控 vs 非受控 → 答反了，已纠正**：
- 学生答"B 受控 A 非受控" ❌ **反了**
- **正确**：A（value+onChange）受控、B（ref）非受控
- **判断标准**：值存在哪、谁说了算
  - **受控**：值在 React state，`value` 决定显示，React 全程控制（value+onChange 接环）
  - **非受控**：值在 DOM 自己身上，React 撒手不管，用 `ref` 临时捞值
- **易错点**：直觉觉得"用 ref 手动操作"像在控制 → 反了，ref 恰恰是"React 不管、需要时去 DOM 捞"= 非受控
- 场景：受控（多数表单，要实时校验/联动）；非受控（简单场景、`<input type="file">` 只能非受控）
- 对比 Vue：`v-model` 本质是受控；Vue 几乎不用非受控，React 因不监听才保留 ref 这条路

**Q2 虚拟 DOM（不清楚 → 补讲）**：
- **一句话**：用 JS 对象描述真实 DOM 长什么样（① 站那个 `{type, props, children}` 就是）
- **为什么要它**：真实 DOM 操作慢（触发 reflow/repaint）；虚拟 DOM 玩法 = state 变→重跑生成新虚拟DOM树→和旧树 diff→算出最小改动→批量更新真实 DOM
- **核心价值**：用快的（diff JS 对象）算出最小改动，减少慢的（真实 DOM 操作）
- **串 ③ 站**："全量重跑"不亏——重跑生成的是虚拟 DOM（JS 对象，便宜），不是直接动真实 DOM

**Q3 Fiber 为什么可中断（不清楚 → 补讲，点到即可）**：
- **不中断的代价**：老 React diff 递归一口气跑完，大组件树 diff 几十~上百 ms，单线程主线程被占满 → 用户点击无反应/输入卡顿/动画掉帧
- **Fiber 解法**：把"一口气跑完的大 diff"切成一小块块工作单元（Fiber 节点），跑几块回头看一眼有没有更急的事（用户输入/动画），有就暂停让路、回头再接着跑
- **钉死**：Fiber = 把大 diff 切成可中断的小块，能暂停/让路/再回来，别卡死界面（Concurrent 的底层基础）
- 深度到此，不钻源码/不手画链表

### 关键盲区修正

1. **React 心智模型（连续第 3 次强调）**："监听 = 重跑"是错的 → React 无监听、无依赖收集，setState 只是触发全量重跑 + diff
2. **受控/非受控答反**：ref = 非受控（React 撒手），value+onChange = 受控（React 全程控制）

### 记忆锚点

> - 受控 = 值在 state、React 控制（value+onChange 环）；非受控 = 值在 DOM、用 ref 临时读
> - 虚拟 DOM = JS 对象描述 DOM，diff 算最小改动，减少昂贵真实 DOM 操作
> - Fiber = 把大 diff 切成可中断小块，别卡死界面
> - React 的"重跑"不是监听，是暴力全量执行 + diff 优化（弥补成本靠不可变/key/memo）

### 🤖 AI 时代视角

- **AI 能做**：写受控/非受控样板、背虚拟 DOM/Fiber 定义
- **AI 替代不了**：
  - 选受控还是非受控（实时校验/联动→受控，文件上传→只能非受控）
  - 理解"全量重跑为何不亏"（虚拟 DOM 便宜、真实 DOM 贵）→ 排查性能问题的基础

**RHF 核心 4 个 API**：register（注册字段）、handleSubmit（提交校验）、formState.errors（错误对象）、setValue/reset（手动操作）

**Zod 职责澄清**（学生说反已纠正）：
- **Zod 负责定义校验规则**（schema：必填/最小长度/正则/格式）

- Zod 附赠 TS 类型推断（`z.infer<typeof schema>`）

**Zod 三个用途**（面试亮点）：RHF 校验 / TS 类型推断 / 前后端同构（同一份 schema Node.js 后端也能用）
