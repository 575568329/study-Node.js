**关键收获**：
- 渲染管线：DOM/CSSOM → Render 树 → **Layout(reflow) → Paint(repaint) → Composite**
- 三档性能开销：几何属性(reflow 最贵) > 外观属性(只 repaint) > transform/opacity(只合成，GPU 最便宜)
- transform 便宜的原因：提升为 GPU 图层"挪贴纸"，坑不动+像素不重画，跳过 ④⑤（跳过是因、快是果）
- 布局抖动（强制同步布局）：读几何值(offsetWidth 等)会逼浏览器立即 reflow → **读写分离**修复
- em 相对父级会逐层累乘（复利失控）；rem 相对根 `<html>`（非 body）永远一把尺
- vw 认视口宽 / vh 认视口高；% 高度需父级有确定高度；vh 移动端跟地址栏打架 → dvh
- 1px 问题根源：DPR≥2 时 1 CSS px = 多个物理像素，细线做不出 → 伪元素 + scaleY(1/DPR)

**错题本**（概念模糊 / 因果倒置，复习重点）：
- 🔴 **判断依据错**：说"background-color 不 reflow 是因为 DOM 没改" → 正确依据是"看改的属性动没动布局"（改 width 不动 DOM 也 reflow）
- 🔴 **因果倒置**：说"transform 性能好所以跳过步骤" → 反了，"跳过 layout/paint 是因，性能好是果"
- 🔴 **概念模糊**：rem 说成"相对 body" → 是根元素 `<html>`（移动端适配设 html 字号的原因）
- 🟡 **计算失误**：100vh 在 1200×800 视口算成 600（抄了宽度）→ vh 认高，应 800
- 🟡 **术语不精**：画线的 `::after` 说成"伪类" → 是伪元素（造元素）；伪类是选状态/位置

**过关题目**（1 个大 KP，深度）：

✅ **Node 模块化**：CJS vs ESM 6 个必知维度

**关键收获**：

1. **`module.exports` vs `exports` 陷阱**（Q2 盲区→已掌握）
   - `exports` 是 `module.exports` 的别名（引用），`exports = { }` 会断引用
   - 改属性用 `exports.xxx`，替换整个对象用 `module.exports`
   - Node 加载时包一层函数：`(function(exports, require, module, __filename, __dirname) { ... })`

2. **JSON 导入差异**（Q3 盲区→已掌握）
   - `require('./data.json')`：零配置，CJS 自动 JSON.parse
   - `import data from './data.json' with { type: 'json' }`：需显式声明
   - 根因：CJS 运行时加载（看到 .json 自动处理）vs ESM 编译时静态分析（需提前知道类型）

3. **循环引用**（核心对比）
   - CJS：返回**半成品快照**（`require` 时 exports 还没赋值的属性 = `undefined`），静默 bug
   - ESM：**直接报错**（`const` 导出的 TDZ 在读未初始化变量时抛 ReferenceError），fail fast
   - ESM 活绑定（Live Binding）：`import` 不拷值，建立指向导出变量的"指针"，随原变量变化
   - ESM 深度优先求值：依赖先于入口执行（b.mjs 先跑，不是 a.mjs）

4. **动态 `import()` vs 静态 `import`**（串起事件循环）
   - 静态 `import { }`：编译时处理，不返回 Promise，不涉及事件循环
   - 动态 `import()`：运行时发起异步加载，返回 Promise，模块求值在 resolve 时同步执行
   - 同步调用返回 Promise ≠ 代码变微任务（**三天串联的根因**："返回 Promise"和"回调变成微任务"是两个阶段）

5. **类型判定规则**（优先级从高到低）
   - `.mjs`（永远 ESM）> `.cjs`（永远 CJS）> package.json `"type"` 字段 > 默认 CJS

### ✅ Node 原生 http 模块

**`req` 是 Readable 流，`req.body` 不存在**：
- 回调在**请求头解析完**就触发，body 还在网络上飘
- 回调时能拿到：`req.method` / `req.url`（只有路径+query）/ `req.headers`（key 全小写）
- **拿不到 `req.body`**——那是 `express.json()` 后来挂上去的
- 设计原因：body 可能 2GB（文件上传），不可能等全到齐才回调 → 做成流让你自己消费

**手动收 body 的正确写法**：
```js
const chunks = []
req.on('data', chunk => chunks.push(chunk))
req.on('end', () => {
  const body = Buffer.concat(chunks).toString('utf8')
})
```
⚠️ **生产 bug**：别写 `body += chunk`——中文 UTF-8 占 3 字节，正好切在 chunk 边界会乱码。必须攒 Buffer 最后一次性解码。

**`res` 是 Writable 流**：
- `res.writeHead()` 必须在 `res.end()` 之前（HTTP 协议规定头先发，写完 body 再改头报 `ERR_HTTP_HEADERS_SENT`）
- `charset=utf-8` 别省，不写中文可能乱码
- **不调 `res.end()` = 请求永久挂起**（浏览器转圈到超时）→ 每个 if 分支后加 `return` 防漏

**Express 到底封装了什么**：
| | 原生 http | Express | Spring MVC |
|---|---|---|---|
| 路由 | `if (req.url === ...)` | `app.post('/x')` | `@PostMapping("/x")` |
| 取 body | 手动收流 | `express.json()` | `@RequestBody` |
| 返 JSON | 手动 stringify | `res.json()` | `@ResponseBody` |

三边同结构：**底层都是流，上层框架 buffer + 反序列化**。

**实战代码**：`projects/nodejs/01-express-demo/http-test.js`（POST 路由 + 流式收 body + 400/404 处理 + error 监听）

### ✅ cluster 多进程（吃满多核）

**核心机制**：只有主进程 `listen`，worker 不 listen
- 主进程收连接 → 通过 IPC 把 socket 句柄传给 worker
- 从 OS 看 3000 端口始终只被 1 个进程占用 → 不冲突
- **cluster 劫持了 `listen`**：worker 里调 `listen` 不真绑端口，只发消息说"我准备好了"

**关键限制：worker 之间不共享内存**
- `let count = 0` 在 4 个 worker 里是 4 份独立变量 → 数据全乱
- 必须外置到 Redis：Session / 缓存 / 计数器 / 限流 / WebSocket 广播
- **回扣 JWT**：无状态所以任何 worker 都能独立验签——07-29 学的"Session 跨服务器问题"在 cluster 里就已出现，不用等多机

**生产用 PM2 不手写 cluster**：
- `pm2 start app.js -i max`（按核数起）/ `pm2 reload`（零停机滚动重启）
- 回扣异步错误处理：`uncaughtException` 兜底后 `process.exit(1)` → 就是让 PM2/cluster 看到非零退出码换干净进程

**对比 Java 并发哲学**：
| | Node | Java (Spring Boot) |
|---|---|---|
| 模型 | 单线程事件循环 + 多进程 | 多线程（Tomcat 默认 200 线程）|
| 吃满多核 | 起 N 进程（cluster/PM2）| JVM 内多线程天然用 |
| 状态共享 | ❌ 进程隔离，必须外置 | ✅ 内存共享（但要加锁）|
| 代价 | 内存 ×N | 并发安全问题（锁/竞态/死锁）|

**根本分歧**：Node 用"进程隔离"换"不用写锁"（单线程天然无竞态），代价是共享状态必须外置。

⚠️ `worker_threads` 是给 **CPU 密集计算**用的（图片/加密/大量计算），不是给 HTTP 并发用的，别搞混。

### 🔴 宏任务 vs 微任务边界（新 KP，标 Again）

**错误**：`req.on('data', ...)` 答成"微任务"
**正确**：`'data'` 是 I/O 事件，**poll 阶段的宏任务**

**这是"await 同步性"混淆的第 4 次变体**：
| 日期 | 错法 | 实际 |
|---|---|---|
| 07-24 | `await async2()` 是微任务 | 函数体同步执行 |

**共同根因**：看到"异步"就归到微任务。

**钉死口诀**：

```js
  const [r2] = await conn.query('UPDATE ... WHERE id = ?', [2])
  if (r2.affectedRows === 0) throw new Error('转入账户不存在')
  await conn.commit()
} catch (err) {
  await conn.rollback()
  throw err
} finally {
  conn.release()
}
```

1. **同一个 conn 贯穿 begin/query/commit/rollback**

## 2026-08-02 下午学习记录 - SSE 流式响应

### 学习内容

**主题**：SSE (Server-Sent Events) 流式响应

**核心突破**：
1. **SSE 协议格式**
   - 服务端三响应头：`Content-Type: text/event-stream` / `Cache-Control: no-cache` / `Connection: keep-alive`
   - 消息格式：`data: xxx\n\n`（双换行是消息终止符，单 `\n` 只分隔多行消息内的字段）
   - 客户端 API：`EventSource` 自动处理重连

2. **流式响应本质**
   - `res.write()` 边缘触发立即发送，不等 `res.end()`
   - 区别于 `await res.json()` 全量缓冲后解析
   - AI 应用流式输出的技术基础

3. **EventSource 生命周期**
   - 服务端 `res.end()` / 网络断开 → 触发客户端 `onerror` → 自动重连（默认 3 秒）
   - 客户端 `es.close()` → 设置 `readyState = CLOSED` → **不触发 `onerror`、阻止重连**
   - 约定：服务端发 `[DONE]` 标记 → 客户端收到后调 `close()` 优雅关闭

4. **技术选型洞察**
   - SSE vs WebSocket：SSE 是单向低成本方案（无协议升级、自动重连、标准 HTTP）
   - AI 对话场景：客户端不回推数据 → WebSocket 双向通信是过度设计
   - 成本对比：SSE 够用就不付 WebSocket 的协议升级和心跳维护成本

5. **生产三大坑**
   - **Nginx 缓冲**：`proxy_buffering off` 或后端 `X-Accel-Buffering: no`（默认攒够 4KB 才转发，几十字节的消息会卡十几秒）
   - **连接泄漏**：`req.on('close')` 监听客户端断开，`clearInterval(timer)` 清理资源
   - **CORS**：`file://` 协议打开 HTML，origin 是 `null`，需要 `Access-Control-Allow-Origin: *`

6. **排查顺序**（面试亮点）
   - 第一步：抓包/DevTools Network 对比服务器发送时间戳 vs 浏览器接收时间戳
   - 第二步：检查 Nginx/网关配置 `proxy_buffering` / `X-Accel-Buffering`
   - 第三步：代码层（`res.write()` 时机、`\n\n` 终止符）

### 理解盲区修正

1. **误认为 `res.write()` 会等流执行完再返回**
   - 错误理解：以为要等所有 `write()` 执行完才发送
   - 纠正：流是边缘触发，每次 `write()` 立即发送，这是 `await res.json()` 行为（全量缓冲），不是流的行为

2. **反向理解 `req.on('close')` 方向**
   - 错误表述："客户端会监听 close 事件"
   - 纠正：服务端的 `req` 对象监听客户端断开事件，方向是客户端发起 → 服务端检测

3. **误以为 `es.close()` 会触发 `onerror`**
   - 错误理解：以为所有断开都触发 `onerror` + 重连
   - 纠正：只有服务端断开（`res.end()` / 网络故障）触发 `onerror` + 自动重连；客户端 `es.close()` 设置 `readyState = CLOSED`，不触发 `onerror`，阻止重连
