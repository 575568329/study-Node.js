### 学习成果

**RocketMQ 消息模型（Day 29）**

**核心：消费组（Consumer Group）——组间复制，组内竞争**
- 不同组之间：每组都收到全量（ES/缓存/统计三个组各处理一遍）
- 同一个组内部：一条消息只给一个实例（库存 3 实例只扣 1 次，自带负载均衡）
- 对比 Dubbo：负载均衡是"调用方选机器"，MQ 是"消费者抢消息"——方向相反目的相同

**组名配置判断标准**：
| 情况 | 组名 |
|------|------|
| 横向扩容（新实例代码一样） | 同一个组名 |
| 新业务方（处理逻辑不同） | 另起组名 |

**广播模式（Broadcasting）**：组内也全量，用得少（典型：每实例刷新本地配置缓存）

**Topic + Tag**：
- Topic = 业务类型（书架），Tag = 子类型分类标签（书架内标签）
- 划分规则：不同业务分 Topic；同一业务子类型用 Tag
- Tag 过滤发生在 **Broker 侧**（不符合的根本不发过来，省网络）
- `consumer.subscribe("ORDER_TOPIC", "pay")` / `"*"` / `"pay || cancel"`

### 今日面试题沉淀（3 道）

1. RocketMQ 一条消息多个服务都要处理 vs 只处理一次，怎么配置？→ 消费组：组间复制（各起组名）组内竞争（同组名）。横向扩容用同组，新业务方另起组
2. Topic 和 Tag 怎么划分？→ 不同业务分 Topic，同一业务子类型用 Tag（订单创建/支付/取消同 Topic 不同 Tag）；Tag 在 Broker 侧过滤
3. 库存 3 实例都收到同一条消息各扣了一次库存，怎么排查？→ 违反组内竞争，大概率 3 实例配了 3 个不同组名（或误开广播模式），查各实例 group 配置统一组名
