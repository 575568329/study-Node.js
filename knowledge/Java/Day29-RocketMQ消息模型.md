## 一、消费组（Consumer Group）—— 最重要的概念

### 核心规则：组间复制，组内竞争

```
场景一：三个下游都要处理"题目删除"
                        Topic：题目删除
                              │
        ┌─────────────────────┼─────────────────────┐
        ↓                     ↓                     ↓
   【ES搜索服务组】       【缓存服务组】         【统计服务组】
        │                     │                     │
      1实例                 1实例                  1实例
   → 组间复制：每组都收到全量 ✓
```

```
场景二：库存服务 3 实例，一条消息只能处理一次
                        Topic：订单扣库存
                              │
                        【库存服务组】
                        ┌─────┼─────┐
                        ↓     ↓     ↓
                      实例1  实例2  实例3
   → 组内竞争：一条消息只给一个实例 ✓ 不会扣 3 次
```

**一句话钉死：不同组之间，每组都收到一份；同一个组内部，一条消息只给一个实例。**

- 组内竞争自带**负载均衡**：10 万条消息摊给 3 个实例，不用写分发代码
- 对比 Dubbo：负载均衡是"调用方选机器"（pull 方向），MQ 是"消费者抢消息"（push 方向）——方向相反，目的相同

### 组名配置判断标准

| 情况 | 判断 | 组名 |
|------|------|------|
| 横向扩容（新实例代码一模一样，为扛更多消息） | 加的是"手脚" | **同一个组名** |
| 新业务方（处理逻辑不同，也要消费这消息） | 加的是"新部门" | **另起组名** |

### 经典故障排查

**症状**：库存 3 实例都收到同一条消息，各扣了一次库存。

**诊断**：违反了"组内竞争"。最可能原因：**3 个实例配了 3 个不同的组名**（MQ 当成 3 个组，组间复制全量下发）；次可能：误开广播模式。

**修法**：查各实例 group 配置，统一组名。

## 二、广播模式（Broadcasting）

默认是**集群模式**（Clustering，即上面的组内竞争）。广播模式 = **同一个组内**每个实例都收到全量。

用得少。典型场景：每个实例本地内存有一份配置缓存，消息来了希望**每个实例都刷新自己那份**。

类比：公司群发通知到 3 个部门（组间复制，默认就有）；部门内一般派一个人办（组内竞争）；只有"每人都要签字"才全员 broadcast。

## 三、Topic 与 Tag

### 划分规则

| 粒度 | 判断 | 举例 |
|------|------|------|
| **Topic** | 业务类型不同 | 订单事件 vs 题目事件 |
| **Tag** | 同一业务的不同子类型 | 订单的创建/支付/取消/发货 |

划太细的坏处：Topic 有运维成本（队列/权限/监控都按 Topic 配），4 种订单事件开 4 个 Topic 是浪费。

类比：**Topic 是书架，Tag 是书架内的分类标签**。"编程语言"是"计算机"的子集，贴标签不开新书架。

### 订阅 API 与 Broker 侧过滤

```java
// 只要"支付"消息
consumer.subscribe("ORDER_TOPIC", "pay");

// 要全部
consumer.subscribe("ORDER_TOPIC", "*");

// 多个 Tag
consumer.subscribe("ORDER_TOPIC", "pay || cancel");
```

**关键**：过滤发生在 **Broker（MQ 服务器）侧**——不符合 Tag 的消息根本不发给消费者，不是收到后在代码里 if 掉。省网络省序列化。

## 五、面试标准答案

> RocketMQ 靠消费组决定消息被谁处理：组间复制——不同组每组都收到全量；组内竞争——同组内一条消息只给一个实例，自带负载均衡。横向扩容用同一个组名，新业务方另起组名。广播模式让组内也全量，适合每实例刷新本地缓存的场景。
>
> Topic 按业务类型划分，同一业务的子类型用 Tag，Tag 过滤在 Broker 侧完成（不符合的不下发）。
>
> 排查"多实例重复消费"：先查各实例 group 配置是否统一（最常见：配了不同组名被当成多个组），再查是否误开广播模式。

## 🤖 AI 时代视角

**被 AI 贬值**：subscribe API 写法、Topic/Tag 配置样板

**AI 时代更值钱**：
- **消费组划分的架构判断**（新服务该并组还是另起组——配错就是重复消费或漏消费事故）
- **"重复消费了"的排查直觉**（第一反应查 group 配置，不是查业务代码）
- **Topic 粒度设计**（开太多 Topic 的运维成本 vs Tag 的取舍）
