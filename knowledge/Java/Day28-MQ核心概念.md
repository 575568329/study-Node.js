## 一、MQ 三大价值

### 1. 解耦（故障隔离）

```
RPC 直连：库存挂了 → 订单跟着挂（依赖传导）
MQ 隔离：库存挂了 → 消息堆在 MQ → 库存恢复接着消费 → 订单全程无感
```

类比：留言板——不关心对方在不在，写完就走。

### 2. 异步

发完消息立刻返回，不等下游处理完（Day 23 已学）。

### 3. 削峰

**秒杀场景**：10 万请求瞬间打来，DB 每秒只扛 5000 写入。

- 不用 MQ：连接池打满 → 全部超时 → 崩
- 用 MQ：10 万请求进队列排队 → 消费者按 5000/秒慢慢消费

**代价**：用户体验从"秒回结果"变"排队中 → 成功"两段式。秒杀页面的"正在排队…"就是这个架构的产物。

## 二、消息可靠性三道防线

消息一生有三个可能丢失的点：

| 丢失环节 | 场景 | 防线 |
|---|---|---|
| ① 发送时丢 | 生产者→MQ 网络传输失败 | **本地消息表**（订单+消息同一事务，定时任务重发） |
| ② 存储时丢 | MQ 收到但没写盘就断电 | **持久化 + 刷盘**（生产必开；RocketMQ 同步刷盘） |
| ③ 消费时丢 | 消费者处理一半崩了 | **ACK 机制**（处理成功才确认，没 ACK 重新投递） |

> 记忆锚点：**表保发送、盘保存储、ACK 保消费**
> 第①道就是 Day 23 本地消息表的闭环。

## 三、ACK 机制 → 重复消费 → 幂等

### ACK 流程

```
消费者收到消息 → 处理（扣库存）
  → 成功 → 回复 ACK → MQ 删消息
  → 失败/崩了 → 没 ACK → MQ 重新投递
```

**隐患**：ACK 回复的网络包丢了 → MQ 重新投递 → **同一消息处理两次**。

### 幂等三方案

```sql
-- 方案 1：唯一索引（DB 层兜底，最硬）
INSERT INTO stock_deduction_log (order_id) VALUES (123);  -- UNIQUE 约束

-- 方案 2：先查后做（业务层）
SELECT * FROM stock_deduction_log WHERE order_id = 123;  -- 查到就跳过

-- 方案 3：Redis setnx（高性能层）
SETNX order:123 1  -- 返回 0 说明已存在
```

### 🔴 先查后做的并发漏洞

两个消费者同时收到重投的消息，**同时**查记录，**都查到"没有"**，**都执行**扣库存——扣两次。

根因："查"和"插"之间有**时间差缝隙**，并发请求都能钻进去。

**兜底是唯一索引**：DB 唯一约束是原子的，第二个 INSERT 直接报错，无缝隙可钻。

> 记忆锚点：**查挡九成，索引兜底**
> 注意因果关系：不是"先查后改消除风险"，是"先查后做本身有风险，唯一索引兜底"。

## 五、面试标准答案

> MQ 三大价值：解耦（下游挂了不影响上游）、异步（发完就走）、削峰（洪峰排队按消费端承受力处理，代价是结果延迟）。
>
> 消息不丢三道防线：发送端本地消息表、存储端持久化刷盘、消费端 ACK 确认。
>
> 重复消费用幂等解决：先查后做挡大部分，唯一索引兜底——先查后做有并发缝隙（两个消费者同时查都查不到会都执行），数据库唯一约束是原子的，才是最后防线。

## 🤖 AI 时代视角

**被 AI 贬值**：MQ API 调用样板、配置文件写法

**AI 时代更值钱**：
- **选型判断**：什么时候该上 MQ（解耦/异步/削峰哪个是主要诉求），什么时候 RPC 够用
- **可靠性设计**：三道防线怎么组合（AI 生成的代码常只发消息不管丢失）
- **幂等设计**：唯一索引兜底的并发意识（AI 很少主动提"先查后做有缝隙"）
- **排查"订单创建了库存没扣"**：按消息生命周三环节定位（发送/存储/消费）
