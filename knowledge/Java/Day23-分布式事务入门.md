## 一、问题从哪来？

### Day 22 发现的问题

```java
@Transactional
public void createOrder(Long userId, Long productId) {
    inventoryService.deductStock(productId, 1);  // RPC 1：扣库存
    orderService.createOrder(userId, productId); // RPC 2：创建订单
}
```

**问题**：
- 不同服务 = 不同进程 = 不同 Connection
- `@Transactional` 无法管理跨服务的 SQL
- 扣库存成功，创建订单失败 → **数据不一致**

---

## 二、单体 vs 微服务事务对比

### 单体应用（Day 20）

```java
@Transactional
public void createOrder() {
    jdbcTemplate.update("UPDATE inventory SET stock = stock - 1");
    jdbcTemplate.update("INSERT INTO orders ...");
}
```

- **同一个 Connection**
- **数据库 ACID** 保证原子性
- 任何一条失败 → 整体 rollback

### 微服务

```
【库存服务】               【订单服务】
  库存数据库                 订单数据库
  Connection A              Connection B
```

- **不同 Connection**
- **数据库 ACID 只管单库**
- 需要**分布式事务方案**

---

## 三、分布式事务 4 种方案

### 方案 1：2PC（两阶段提交，强一致性）

**原理**：协调者统一控制

```
阶段 1：Prepare（准备）
  → 协调者问库存服务："能扣库存吗？"
  → 协调者问订单服务："能创建订单吗？"
  → 都回答"可以"（锁资源，不提交）

阶段 2：Commit（提交）
  → 协调者通知所有参与者："提交"
  → 都提交成功
  
【任何一个回答"不行"】
  → 协调者通知所有参与者 rollback
```

**优点**：强一致性（要么全成功，要么全失败）

**缺点（致命）**：
- **同步阻塞**：prepare 阶段锁资源 → 性能差
- **单点故障**：协调者挂了 → 参与者一直等
- **数据不一致风险**：commit 阶段网络故障

**适用场景**：银行转账等**强一致性 > 性能**（很少用）

---

### 方案 2：TCC（Try-Confirm-Cancel，最终一致性）

**原理**：业务层实现三个方法

```java
interface InventoryService {
    void tryDeduct(Long productId, int count);     // 预扣（冻结）
    void confirmDeduct(Long productId, int count); // 确认扣
    void cancelDeduct(Long productId, int count);  // 取消（解冻）
}
```

**执行流程**：

```
Try 阶段（预留资源）
  库存服务：stock_frozen += 1（冻结库存，不减 stock）
  订单服务：创建"待确认"订单
  账户服务：balance_frozen += 100（冻结余额）
  ↓ 都成功
  
Confirm 阶段（真正执行）
  库存服务：stock -= 1, stock_frozen -= 1
  订单服务：订单状态 → "已支付"
  账户服务：balance -= 100, balance_frozen -= 100
  
【如果 Try 任何一个失败】
  
Cancel 阶段（补偿回滚）
  库存服务：stock_frozen -= 1（解冻）
  订单服务：删除待确认订单
  账户服务：balance_frozen -= 100（解冻）
```

**对比 2PC**：
- 2PC：数据库层面锁资源
- TCC：**业务层面冻结字段**（需要 `_frozen` 字段）

**优点**：
- **非阻塞**：Try 只是冻结，不锁表
- **高性能**：适合高并发

**缺点**：
- **开发成本高**：每个服务要实现 3 个方法
- **补偿逻辑复杂**：Cancel 要考虑幂等、重试

**适用场景**：电商下单、支付等**高并发 + 最终一致性**

---

### 方案 3：Saga（长事务，最终一致性）

**原理**：本地事务 + 补偿事务

```
【正向流程】
订单服务：createOrder() ✅
库存服务：deductStock() ✅
    ↓ 都成功
    
【补偿流程】（任何一步失败）
订单服务：createOrder() ✅
库存服务：deductStock() ❌ 失败
    ↓ 触发补偿
订单服务：cancelOrder()  ← 补偿事务（撤销订单）
```

**和 TCC 对比**：
- TCC：预留资源（Try）→ 确认（Confirm）
- Saga：**直接执行**（正向流程）→ 失败时**补偿**（反向撤销）

**优点**：
- **实现简单**：只需写补偿逻辑，不需要 Try 预留
- **长流程适用**：适合跨很多服务

**缺点**：
- **中间状态可见**：正向流程已提交，失败时才补偿 → 用户可能看到"订单一闪而过"
- **补偿不一定成功**

**适用场景**：长流程业务（OTA 订机票+订酒店+订车）

---

### 方案 4：MQ 最终一致性（异步，最终一致性）⭐

**原理**：消息队列 + 异步补偿

```
1. 订单服务：本地事务
   BEGIN
     INSERT INTO orders ...
     INSERT INTO message_table (event='ORDER_CREATED', productId=123)
   COMMIT
   
2. 定时任务：扫描 message_table → 发送到 MQ

3. 库存服务：监听 MQ → 收到消息 → 扣库存

【扣库存失败】
  → MQ 自动重试（重新投递消息）
  → 超过重试次数 → 死信队列 → 人工处理
```

**关键技术点**：
- **本地消息表**：保证"创建订单+发消息"的原子性（同一个本地事务）
- **幂等处理**：消息可能重复，扣库存要幂等
- **死信队列**：重试多次仍失败的消息

**优点**：
- **性能最好**：异步，不阻塞主流程
- **实现简单**：借助 MQ 的重试机制

**缺点**：
- **最终一致性**：有短暂不一致窗口（订单创建了，库存还没扣）
- **消息可能丢失/重复**

**适用场景**：**大部分互联网公司的首选**（电商、支付等）

---

## 四、4 种方案对比表

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|---------|
| **2PC** | 强一致 | 差（阻塞） | 低（数据库支持） | 银行转账（很少用） |
| **TCC** | 最终一致 | 好 | 高（3个方法+冻结字段） | 电商下单、支付 |
| **Saga** | 最终一致 | 好 | 中（补偿逻辑） | 长流程（OTA订票） |
| **MQ** | 最终一致 | 最好（异步） | 中（消息表+幂等） | **大部分场景首选** |

---

## 五、选型铁律

### 按业务需求选

| 需求 | 方案 |
|------|------|
| 强一致性 > 性能（银行转账） | 2PC |
| 高并发 + 最终一致（电商下单） | **MQ** 或 TCC |
| 长流程（跨很多服务） | Saga |
| 大部分互联网场景 | **MQ** |

### 为什么大部分公司用 MQ？

1. **性能好**：异步非阻塞，不影响主流程
2. **可接受短暂不一致**：订单创建后几秒才扣库存，用户可以接受
3. **降级容错**：库存服务挂了，订单仍可创建（MQ 消息堆积，服务恢复后消费）
4. **实现成本低**：借助现成 MQ（RabbitMQ/Kafka），不需要重写业务逻辑

## 七、面试标准答案

> 单体应用用数据库 ACID 保证事务，微服务因为不同服务有不同 Connection 无法共享事务，需要分布式事务方案。
>
> 2PC 强一致但性能差（同步阻塞），很少用。TCC 业务层实现 Try-Confirm-Cancel，Try 冻结资源不阻塞，适合高并发。Saga 直接执行+补偿，适合长流程。MQ 最终一致性异步非阻塞性能最好，大部分公司首选。
>
> 选型看需求：强一致用 2PC，高并发用 MQ/TCC，长流程用 Saga。
