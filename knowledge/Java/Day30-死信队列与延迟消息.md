## 一、死信队列（Dead Letter Queue）

### 为什么不能丢弃？

消息 = **业务事实**（"订单 123 已支付"）。丢消息 = 业务在下游永久丢失：

```
用户付了钱 → 消息 → 库存消费者一直失败（库存表被锁/代码 bug）
  → 重试 16 次（RocketMQ 默认）全失败
  → ❶ 直接丢弃 → 钱扣了货永远不发 → 客诉/资损
  → ❷ 进死信队列 → 消息躺着，等人来救
```

### 机制

- 消费重试超过次数（默认 16）→ 自动转入死信 Topic
- 命名：`%DLQ%消费组名` —— **每个消费组一个死信 Topic**（失败按组隔离，Day 29 消费组概念的延续）
- **本质：带回收功能的垃圾桶，不是焚化炉**

### 死信处理三方式（按自动化程度）

```
① 人工处理（最常见）
   运维监控死信队列（告警）→ 排查失败原因 → 修好 bug → 控制台重新投递

② 程序化兜底
   专门的死信消费者订阅 %DLQ% Topic → 存错误表 + 通知（钉钉/邮件）→ 转人工

③ 定时自动重投
   低峰期（凌晨）自动把死信重投回原 Topic —— 适合临时性失败（DB 抖动）
```

**核心思想**：失败的消息不是垃圾，是**没有完成的工作单**，要进入异常处理流程而不是消失。

> 定位：Day 28 三防线第③道（ACK 保消费）的延伸——ACK 保"没处理完不确认"，死信保"确认失败的也有去处"。

## 二、延迟消息

### 场景：下单 30 分钟不支付自动取消

**笨办法（定时扫表）的问题**：
- 1000 万行订单表每分钟全表扫 → DB 压力大
- 精度差：最快也要等下一个扫描周期

### 延迟消息方案

```
创建订单时：
  发延迟消息「订单 123 取消检查」，延迟 30 分钟
  MQ 先存着不投递
        ↓ 30 分钟后自动投递
  消费者收到 → 查订单 123 当前状态：
    已支付 → 什么都不做
    未支付 → 取消订单 + 释放库存
```

| | 定时扫表 | 延迟消息 |
|---|---|---|
| DB 压力 | 每分钟全表扫 | 零（消息存 MQ） |
| 精度 | 差一个扫描周期 | 精确 30 分钟 |
| 分布式 | 多实例竞争问题 | 天然无竞争 |

### 实现细节（面试加分）

- RocketMQ **4.x：固定 18 个延迟级别**（1s/5s/10s/30s/1m…30m/1h/2h），`setDelayTimeLevel(16)` = 30min
  - 为什么固定？实现是"每个级别一个定时队列，到点搬进真实 Topic"——任意时间会让队列数爆炸
- RocketMQ **5.x：支持任意时间戳**

### 模式精髓：先查再决定

消费者拿到消息**不直接执行业务，先查当前状态再决定**——30 分钟里世界可能已经变了（用户付款了）。

> 串联：和 React stale closure 同一哲学——**消息是发出时刻的快照，执行时必须重看现实**。

## 四、面试标准答案

> 消费重试 16 次失败的消息进死信队列（%DLQ%消费组名，按组隔离），不丢弃——消息是业务事实，丢了就是资损。处理方式：人工修 bug 后重投 / 程序化兜底存错误表+告警 / 低峰定时自动重投。
>
> 30 分钟自动取消用延迟消息：下单时发延迟 30 分钟的消息，到点消费者查订单当前状态再决定是否取消（不能直接取消，消息是快照，用户可能已付款）。对比扫表：DB 零压力、时间精确、天然分布式。
>
> RocketMQ 4.x 只有固定 18 个延迟级别（每级别一个定时队列的实现决定），5.x 支持任意时间戳。
