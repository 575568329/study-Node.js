## Q1：ref vs reactive + 为什么 .value ✅

**区别**：
- **ref**：存基本类型（也兼容对象），用时要 `.value`
- **reactive**：存对象，直接用属性名，不用 `.value`

**为什么 ref 要 .value**：
- ref 底层是 **RefImpl 类的实例**（new 的是类实例，不是函数）
- JS 没法拦截"读裸变量"，只能拦"读对象属性"
- 所以强行包一层对象，用 `.value` 这个固定属性名去触发 **get/set**
- `.value` 就是触发 get/set 的钥匙

```javascript
class RefImpl {
  constructor(value) { this._value = value; }
  get value() { track(); return this._value; }   // 读 → 依赖收集
  set value(v) { this._value = v; trigger(); }    // 写 → 触发更新
}
const count = new RefImpl(0);
count.value++;  // 触发 get + set
```

**为什么 reactive 不用 .value**：
- reactive 用 **Proxy** 拦截整个对象的每个属性
- 对象天然有多个属性，直接用属性名（user.age），Proxy 就能拦到，不需要额外的 .value

| | ref | reactive |
|---|---|---|
| 底层 | RefImpl 类 + get/set | Proxy 代理整个对象 |
| 拦截 | `.value` 一个属性 | 对象每个属性 |
| 为什么 | 基本类型没法拦,包对象 | 对象天然多属性,Proxy 全拦 |

**面试一句话**：ref 用 .value 是因为基本类型没法拦，只能包成对象用 .value 触发 get/set；reactive 用 Proxy 直接拦每个属性，所以用属性名，不需要 .value。

## Q2：Vue3 为什么用 Proxy 替代 defineProperty ✅

**根因：拦截粒度不同。**
- defineProperty：**属性级**粒度（per-property），逐个属性装"传感器"，漏装就拦不到
- Proxy：**对象级**粒度（per-object），整个对象套代理，任何操作都过"大门"被拦

**Vue2 (defineProperty) 三大缺陷**：
1. **新增属性不响应**：`vm.user.age = 29` 不更新（要 `Vue.set`）
2. **删除属性不响应**：`delete vm.user.name` 不更新
3. **数组下标/length 不响应**：`vm.list[0] = x` 不更新（Vue2 hack 7 个数组方法）

根因：defineProperty 只能拦"初始化时存在的属性"，涉及不存在的属性就拦不到。

**Vue3 (Proxy) 全解决**：
- Proxy 拦截整个对象，新增/删除/数组下标**天然响应**
- 删除属性走 `deleteProperty` 拦截器，也能监听
- 能拦截 **13 种操作**（get/set/has/deleteProperty/ownKeys...）

| | defineProperty (Vue2) | Proxy (Vue3) |
|---|---|---|
| 粒度 | 属性级 | 对象级 |
| 新增属性 | ❌ 要 Vue.set | ✅ 天然响应 |
| 删除属性 | ❌ | ✅ deleteProperty |
| 数组下标 | ❌ hack 7 方法 | ✅ 天然响应 |
| 拦截操作 | 只有 get/set | 13 种 |

**面试一句话**：Vue2 用 defineProperty 是属性级粒度，只能拦初始化时存在的属性，新增/删除/数组下标都不响应；Vue3 用 Proxy 是对象级粒度，整个对象的操作都拦截，全部天然响应。

## Q3：依赖收集（track/trigger）✅

**核心机制**：Vue 怎么知道"数据变了要更新哪块 DOM"？→ **提前记录谁用了我，变了再通知**。

**effect 是什么**：会用到响应式数据的"东西"（页面渲染、computed、watch），Vue 统一叫 effect。
- **effect 是 Vue3 自己加的，原生 JS 没有**
- 业务代码几乎不直接写 effect，Vue 背后帮你把渲染/computed/watch 包装成 effect
- effect 执行时读了响应式数据 → 触发 get → track 记录

**track（get 时执行）**：记录"当前 effect 依赖了我这个数据"
```javascript
get value() {
  track(this);           // 把 activeEffect 存进依赖集合
  return this._value;
}
```

**trigger（set 时执行）**：通知"所有依赖我的 effect 重新执行"
```javascript
set value(newVal) {
  this._value = newVal;
  trigger(this);         // 取出存的 effect,逐个重新执行 → 页面更新
}
```

**三层依赖结构（记死）**：
```
WeakMap (仓库)        ← 对象 → depsMap,弱引用防内存泄漏
  └─ depsMap (Map)    ← 属性名 → Set,区分是哪个属性的依赖
       └─ Set<effect> ← 一个属性被多个 effect 依赖(一对多)
```

每层解决一个问题：
1. WeakMap：区分"哪个对象"（弱引用,对象销毁自动回收,防泄漏）
2. depsMap(Map)：区分"哪个属性"（精确更新,改 name 不通知 age 的依赖）
3. Set：一个属性被多个 effect 依赖（一对多）

**为什么用 WeakMap 不用 Map**：弱引用，对象销毁时依赖记录自动被垃圾回收，防内存泄漏。

**面试一句话**：track 在 get 时记录"当前 effect 依赖了我"，trigger 在 set 时通知"所有依赖我的 effect 重新执行"。用 WeakMap→Map→Set 三层结构，精确到属性级更新，所以不是整个页面重渲染。

### 关键补充：ref vs reactive 的依赖存储位置（重要区别！）

**依赖存哪不一样**：
- **ref**：依赖存在**实例自己的 `dep` 属性**上（`num.dep = Set<effect>`）
- **reactive**：依赖存在**外部全局 targetMap（WeakMap）**里，**不碰原对象**

```
【ref】依赖在实例自己身上
num (RefImpl 实例)
├── _value = 0          ← 值
└── dep = Set<effect>   ← 依赖(自己挂的属性)

【reactive】依赖在外部全局仓库,obj 保持干净
targetMap (WeakMap)
└─ key: obj → depsMap (Map)
                ├─ 'name' → Set<effect>
                └─ 'age'  → Set<effect>
```

**为什么 reactive 不把依赖存在 obj 里**：
1. 不能污染用户的对象（obj 是用户传进来的，Vue 不能往里塞东西）
2. ref 能挂自己的属性，是因为 RefImpl 实例是 Vue 造的，可以随便挂

**为什么 reactive 必须用 WeakMap，ref 不用**：
- reactive 要区分"哪个对象的依赖"（多个对象），key 是对象，弱引用防泄漏
- ref 实例自己就是独立单位，依赖挂自己身上即可

**reactive 的查找路径（track 干的事）**：
```javascript
targetMap.get(obj).get('属性名').add(effect)
//  obj → depsMap → 'name' → Set → 把 effect 存进去
```

**⚠️ 易混点**：
- reactive 的 depsMap key 是**对象属性名**（'name'、'age'）
- ref 不走 depsMap，直接 dep = Set（因为只有 .value 一个属性，不用区分）

**dep 能直接访问吗**：不能，是 Vue 内部属性，业务代码访问不到。看依赖用 Vue Devtools。

### 版本说明 & 参考来源（避免看源码困惑）

**⚠️ 版本差异**：Vue 3.4 重构了响应式系统，引入了 `Dep` 类（不再用裸 `Set`）。
- 本讲稿用 `Set<effect>` 是**概念简化**，理解依赖收集完全够用
- 看源码时：3.4+ 的 `dep` 是 `Dep` 实例（内部还是装 effect），概念一致
- 面试讲概念用 Set/Dep 都行，核心是"装 effect 的集合"

**已查证正确（2026-07-17 对比权威资料）**：
- 三层结构 `targetMap(WeakMap) → depsMap(Map) → dep(Set)`：✅ 正确
  来源：Vue 官方文档、edison1105 深度文章、dev.to 实现解析
- track 在 get / trigger 在 set：✅ 正确
- WeakMap 防内存泄漏：✅ 正确
- ref 依赖挂实例自身、reactive 在全局 targetMap：✅ 正确

## Q4：Composition API vs Options API ✅

**Options API 的痛点**：按"选项类型"组织（data 一堆、methods 一堆、mounted 一堆），
同一功能的代码**散落在不同选项**，代码多要来回滑动找。

**Composition API 解决两个问题**：

**① 逻辑组织**：按"功能逻辑"组织，相关代码聚在一起
```vue
<script setup>
// 登录逻辑 - 聚在一起
const { username, password, login } = useLogin()
// 主题逻辑 - 聚在一起
const { theme, toggleTheme } = useTheme()
</script>
```

**② 逻辑复用（杀手锏）**：用 Composable 函数替代 mixin
| | Options API (mixin) | Composition API (Composable) |
|---|---|---|
| 命名冲突 | ❌ 容易冲突 | ✅ 解构重命名解决 |
| 来源不清 | ❌ 不知道哪个 mixin | ✅ 看函数调用就知道 |
| TS 支持 | ❌ 差 | ✅ 完美 |
| 灵活性 | ❌ 固定结构 | ✅ 函数随便组合 |

**面试一句话**：Composition API 解决逻辑组织（代码聚集）+ 逻辑复用（Composable 替代 mixin，避免命名冲突、来源清晰、TS 支持好）。

## Q5：Composable（组合式函数）+ computed/watch/watchEffect ✅

### Composable 三个规则

1. **必须 `use` 开头**（约定，一眼看出是 Composable）
2. **返回必须是响应式数据**（ref/reactive）—— 返回普通变量解构后**丢失响应式**
3. **在 setup 顶层同步调用**（onMounted 等生命周期才生效；异步里调就晚了）

```javascript
// composables/useCounter.js
import { ref, computed, onMounted } from 'vue'
export function useCounter(initial = 0) {
  const count = ref(initial)
  const double = computed(() => count.value * 2)
  function increment() { count.value++ }
  onMounted(() => console.log('挂载了'))
  return { count, double, increment }   // 返回 ref,保持响应式
}

// 组件里用
const { count, increment } = useCounter(10)
const { count: count2 } = useCounter(0)   // 复用第二份,重命名
```

**坑**：`return { ...reactive对象 }` 解构丢响应式 → 用 `toRefs()` 或整个对象返回。

### computed vs 普通函数：核心是"缓存"

**普通函数每次调用都重算**；**computed 有缓存，依赖没变就不重算**。
```javascript
const double = computed(() => count.value * 2)
double.value   // 算一次
double.value   // 不算!用缓存(count 没变)
count.value = 5
double.value   // 算!依赖变了
```
**缓存用处**：昂贵计算（过滤万条数据）用 computed，模板渲染多次也只算一次。

### watch vs watchEffect

| | watch | watchEffect |
|---|---|---|
| 立即执行 | ❌ 不执行 | ✅ 立即执行一次 |
| 监听谁 | 显式指定 | 自动追踪（读了谁就监听谁）|
| 拿旧值 | ✅ 能拿 newVal/oldVal | ❌ 拿不到 |

**⚠️ 易混点**：watchEffect 才是"立即执行+自动追踪"，watch 是"只监听+不立即+要指定"。别记反。

### 场景选择

| 场景 | 用啥 |
|---|---|
| 根据数据算新数据（派生、只读） | **computed**（有缓存）|
| 数据变了做副作用（请求、改 DOM） | **watch**（拿新旧值）|
| 副作用+立即执行+多依赖 | **watchEffect** |

**一句话**：computed 是派生数据（只读、缓存），watch/watchEffect 是监听变化做副作用（watch 显式+拿旧值，watchEffect 自动+立即执行）。

## Q6：生命周期钩子 ✅

**Vue2 → Vue3 对照表**：

| Vue2 (Options) | Vue3 (Composition) | 时机 |
|---|---|---|
| beforeCreate | setup() 本身 | 创建前 |
| created | setup() 本身 | 创建后 |
| beforeMount | onBeforeMount | 挂载前 |
| mounted | **onMounted** | 挂载后（DOM 可用）|
| beforeUpdate | onBeforeUpdate | 更新前 |
| updated | onUpdated | 更新后 |
| beforeDestroy | **onBeforeUnmount** ⭐ | 卸载前（改名！）|
| destroyed | **onUnmounted** ⭐ | 卸载后（改名！）|

**三个关键变化**：
1. **beforeCreate/created 没了** → 直接在 setup 顶层写（setup 本身就是这俩时机）
2. **destroyed → unmounted**（卸载改名：destroy→unmount）
3. **统一加 `on` 前缀**

```vue
<script setup>
import { onMounted, onUnmounted } from 'vue'
console.log('created 逻辑')          // 顶层直接写
onMounted(() => { /* DOM 可用,请求数据 */ })
onUnmounted(() => { /* 清定时器/监听 */ })
</script>
```

**最常用两个**：
- **onMounted**：挂载后（DOM 可用）→ 操作 DOM、请求接口、初始化
- **onUnmounted**：卸载前 → 清定时器、移除事件监听、取消请求

**为什么 onMounted 能拿 DOM，setup 顶部拿不到**：setup 执行时还没挂载 DOM，
onMounted 是**挂载后**才跑，此时 DOM 已生成。

**⚠️ 易混点**：onMounted = 挂载**后**（DOM 可用）；onBeforeMount = 挂载**前**。
带 `on` + 名字就是时机，Mounted=已挂载，别记成"挂载前"。

## Q7：组件通信（父子 + 跨层级）✅

### 1. 父→子：props + defineProps

```vue
<!-- 子组件 -->
<script setup>
const props = defineProps({ msg: String })   // 接收
console.log(props.msg)
</script>
```

### 2. 子→父：emit + defineEmits + @监听

```vue
<!-- 子组件 -->
<script setup>
const emit = defineEmits(['update'])          // 声明能触发的事件
function onClick() {
  emit('update', '新值')                       // 触发事件,带数据
}
</script>

<!-- 父组件 -->
<Child @update="handleUpdate" />              <!-- 监听事件 -->
```

**四个 API 各司其职（别混）**：
| API | 谁用 | 干啥 |
|---|---|---|
| `defineProps` | 子 | **接收**父传的数据 |
| `defineEmits` | 子 | **声明**子能触发哪些事件 |
| `emit()` | 子 | **触发**事件,把数据传回父 |
| `@update` | 父模板 | **监听**事件,绑定处理方法 |

**数据流向**：父→子走 props，子→父走 emit + @监听。

**Vue3 vs Vue2 变化**：
1. `props` → `defineProps()`（编译宏，不用 import）
2. `this.$emit` → `emit()`（没了 this，先 defineEmits 拿到 emit 函数）
3. 新增 `defineEmits` 显式声明事件（Vue2 的 emits 可选，Vue3 鼓励显式写）

`defineProps/defineEmits` 是**编译宏（macro）**，不是真实函数，不用 import，编译时自动处理。

### 3. 父操作子：ref + defineExpose ⭐ Vue3 新增

**Vue3 默认全隐藏**：`<script setup>` 里的东西父组件拿不到，必须子组件 `defineExpose` 主动暴露。

```vue
<!-- 子组件 -->
<script setup>
const count = ref(0)
function doSomething() { count.value++ }
defineExpose({ count, doSomething })    // ★ 主动暴露,不写父拿不到
</script>

<!-- 父组件 -->
<template>
  <Child ref="childRef" />
  <button @click="callChild">调用子方法</button>
</template>
<script setup>
const childRef = ref(null)
function callChild() {
  childRef.value.doSomething()    // 通过 ref 直接调
}
</script>
```

**为什么 Vue3 加 defineExpose**：解决 Vue2 封装性差（全暴露，父能随便改子内部）。
封装思想：**访问权限由被访问方控制**，"我让你改你才能改"（和 Java private/public 一个道理）。

| | Vue2 | Vue3 `<script setup>` |
|---|---|---|
| 默认暴露 | 全暴露 | **全隐藏** |
| 怎么暴露 | 不用管 | `defineExpose({ })` |
| 父怎么调 | `this.$refs.child.xxx` | `childRef.value.xxx` |

### 4. 跨层级：provide / inject

**解决痛点**：props 一层层传（prop drilling）→ 中间层被迫当传话筒，代码又臭又长。

```
provide/inject: 爷 ──provide──→ ...（中间层无感）... ──inject──→ 孙
```

```vue
<!-- 祖先（提供）-->
<script setup>
import { provide, ref } from 'vue'
const theme = ref('dark')
provide('theme', theme)        // provide(键, 值)
</script>

<!-- 后代（注入，隔几层都行）-->
<script setup>
import { inject } from 'vue'
const theme = inject('theme')  // inject(键)
</script>
```

**三个关键点**：
1. **单向**：只能祖先 → 后代，不能反向
2. **推荐 Symbol 当 key**：防字符串 key 冲突
3. **响应式坑**：后代 inject 后改 `.value` 会影响祖先 → 难维护

**最佳实践（封装思想）**：只提供方法，数据只读
```javascript
const theme = ref('dark')
const toggleTheme = () => { /* 改 theme */ }
provide('theme', { theme: readonly(theme), toggleTheme })
// 只暴露 get（读）+ 方法,不暴露 set（写）
```

### 通信方式选型

| 场景 | 用啥 |
|---|---|
| 父子通信 | props / emit |
| 父直接操作子 | ref + defineExpose |
| 跨层级（深度嵌套）| provide / inject |
| 任意组件、全局状态 | Pinia（状态管理）|

**一句话**：父子用 props/emit，父操作子用 ref+defineExpose（Vue3 强制封装），跨层级用 provide/inject（单向、推荐只读+方法），全局用 Pinia。

## Q8：v-model 原理 ✅

**本质**：v-model 是**语法糖**，拆开是 `prop + 事件`。

| | Vue2 | Vue3 |
|---|---|---|
| 默认 prop 名 | `value` | `modelValue` |
| 默认事件名 | `input` | `update:modelValue` |
| 多个 v-model | ❌ 只能一个（要用 .sync）| ✅ `v-model:名字` 随便几个 |

```vue
<!-- 父 -->
<Child v-model="message" />
<!-- 等价于 -->
<Child :modelValue="message" @update:modelValue="message = $event" />

<!-- 多个 v-model -->
<UserForm v-model:name="userName" v-model:age="userAge" />
```

```vue
<!-- 子组件 -->
<script setup>
const props = defineProps({ modelValue: String })           // 接收
const emit = defineEmits(['update:modelValue'])              // 声明事件(必须叫这个)
function onInput(e) { emit('update:modelValue', e.target.value) }  // 触发
</script>
```

**Vue3 重大改进**：`v-model:名字` 支持多个双向绑定，把 Vue2 的 .sync 合并了。

**修饰符**：
- `v-model.trim`：去首尾空格（用户名、邮箱）
- `v-model.number`：转数字（input value 默认是字符串，age、价格要数字）
- `v-model.lazy`：失焦/回车才更新（非每次输入）
- 原理：修饰符作为 `modelModifiers` prop 传给子组件，子组件自己处理

**一句话**：Vue3 v-model = `modelValue` prop + `update:modelValue` 事件的语法糖，支持 `v-model:名字` 绑多个。

## Q9：v-if/v-show + key + nextTick ✅

### 1. v-if vs v-show

| | v-if | v-show |
|---|---|---|
| 原理 | **不渲染 DOM**（false 时根本不建）| **渲染了但隐藏**（`display: none`）|
| 切换开销 | 大（反复创建/销毁）| 小（只改 CSS）|
| 初始开销 | 小（false 时不建）| 大（总要先建）|

**怎么选（看切换频率，不是 DOM 大小）**：
- **频繁切换**（tab、折叠面板）→ **v-show**（切换开销小）
- **很少切换/初始条件**（登录态、权限）→ **v-if**（初始开销小）

**口诀**：频繁切用 v-show，条件渲染用 v-if。

### 2. v-if 和 v-for 一起用的坑

**Vue2**：v-for 优先级 **高于** v-if → 每次循环都判断，浪费性能
**Vue3**：v-if 优先级 **高于** v-for（反过来了！）→ 拿不到循环变量，报错/失效

**正确做法**（v-if 要用 v-for 的变量时，官方推荐两种）：
```vue
<!-- ① 用 computed 先过滤(推荐) -->
<li v-for="user in activeUsers">{{ user.name }}</li>
<!-- const activeUsers = computed(() => users.value.filter(u => u.active)) -->

<!-- ② 用 <template v-for> 包裹,v-if 放里面(官方推荐) -->
<template v-for="user in users" :key="user.id">
  <li v-if="user.active">{{ user.name }}</li>
</template>
```

> 注：如果是"控制整个列表显隐"（v-if 不用 v-for 的变量，如 `v-if="showList"`），
> 直接把 v-if 放外层容器：`<ul v-if="showList"><li v-for="..."></li></ul>`。

### 3. key 的作用

**本质**：Vue 的 **diff 算法**靠 key 判断节点身份——"复用旧节点，还是新建一个？"

**为什么不能用 index 当 key**（不是"易重复"，是"错位"）：
- index 和数据项**不是稳定绑定**的
- 删除/插入中间项 → index 重新编号 → 节点被错误复用
- **Bug 1**：表单状态错乱（删 A 后 B 的输入框残留 A 的内容）
- **Bug 2**：性能差（后面所有项都要改内容）

```vue
<li v-for="item in list" :key="item.id">   <!-- ✅ 稳定唯一标识 -->
<li v-for="(item,i) in list" :key="i">     <!-- ❌ 删中间项会错位 -->
```

**唯一例外能用 index**：纯展示、永不增删、无状态的静态列表。

### 4. nextTick

**作用**：把回调放到**下次 DOM 更新后**执行（底层用微任务 `Promise.then`）。

**为什么需要**：Vue 改数据后**异步更新 DOM**（为性能批量更新），改完立刻拿 DOM 拿到旧的。

```javascript
count.value++
console.log(box.textContent)         // 旧值!
nextTick(() => {
  console.log(box.textContent)        // 新值 ✅
})
```

**典型场景**：改完数据要操作 DOM（focus 输入框、拿元素宽高、初始化第三方库）。
