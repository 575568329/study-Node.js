# 面试题：策略模式与向量存储

---

## Q1: 策略模式在什么场景下使用？你项目中是怎么应用的？

**我的回答**：
> 策略模式在需要多种实现的时候使用，我的项目中向量数据的保存用了两种方式：一种是 Chroma 数据库保存，另外一种是 JSON 文件保存，根据环境变量来判断。运行时切换我不知道怎么进行。

**补充**：运行时切换 = 不改代码，只改配置就能切换实现。改 `.env.local` 的 `VECTOR_STORE=chroma/file`，代码自动走不同分支。

**核心场景**：同一个功能有多种实现方式，需要在运行时切换，且业务代码不应关心底层实现。

**项目应用**：
- VectorStore 接口定义了 3 个方法（addVectors / similaritySearch / deleteCollection）
- ChromaStore 实现调 Chroma API，FileStore 实现用 JSON 文件 + 手写余弦相似度
- 工厂函数 `getVectorStore()` 读取 `VECTOR_STORE` 环境变量，返回对应实例
- 业务代码只依赖接口，切换实现只改配置不改代码

**扩展性**：新增向量库（如 Pinecone），只需新增实现类 + 改工厂函数，业务代码零改动。

## Q2: 余弦相似度 vs 欧氏距离的区别和适用场景？

**我的回答**：
> 余弦相似度原理是根据一组数据对另外一组数据的相似性是否更高，更高的就更接近正确回答。为什么用余弦而不是欧式距离，我不知道。

**补充**：余弦比较的是"方向"（像不像），欧氏比较的是"距离"（差多少）。文本语义关心方向，所以用余弦。

**余弦相似度**：比较两个向量的**方向**，忽略长度。范围 0~1，越接近 1 越相似。

**欧氏距离**：计算两个向量的**直线距离**。值越小越相似。

**文本语义场景用余弦**：
- "React" 和 "React React" 语义相同但向量长度不同
- 余弦只看方向 → 相似度 = 1（完全相同）
- 欧氏会算出距离 ≠ 0 → 误判为不同

**选型原则**：
| 场景 | 用什么 | 原因 |
|------|--------|------|
| 文本语义匹配 | 余弦相似度 | 关心"像不像"（方向） |
| 地理位置/物理距离 | 欧氏距离 | 关心"差多少"（距离） |
| 用户评分推荐 | 欧氏距离 | 评分绝对值有差异（[5,5,5] vs [1,1,1]） |
| 异常检测 | 欧氏距离 | 离群点距离大 |

## Q3: 向量存储层和业务数据层为什么要分开设计？

**我的回答**：
> 将业务的和数据的分开，避免不需要数据的时候总是拿到数据。

**补充**：更准确的说法是——向量存储做相似度检索（专业能力），db.ts 做元数据管理（标准 CRUD）。职责不同、变化频率不同，分开后换向量库不影响业务逻辑。

**关注点分离**：
- 向量存储层：负责相似度检索（专业能力），存向量 + 文本内容
- 业务数据层（db.ts）：负责元数据 CRUD，存名称、时间、文件名、数量

**为什么要分开**：
1. **职责不同** — 向量检索是数学计算，元数据管理是标准 CRUD
2. **变化频率不同** — 向量库可能从 Chroma 换到 Pinecone，但元数据管理逻辑不变
3. **性能特征不同** — 向量检索是重计算，元数据查询是轻量操作
4. **独立扩展** — 大数据量时向量库需要单独扩容，元数据不需要

**判断标准**：如果一个信息"检索时不需要"，就不属于向量存储层。
