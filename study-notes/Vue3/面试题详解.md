## 1. Vue 3 为什么引入 Composition API？Options API 有什么问题？

### 核心回答（三层）

**第一层：代码组织**
- Options API 按选项类型分散（data/computed/methods/watch），同一功能代码被拆散
- Composition API 按**功能聚合**，用 setup 或 `<script setup>` 组织

```vue
<!-- Options API：同一功能的代码分散在 4 个地方 -->
<script>
export default {
  data() {
    return { keyword: '', searchResults: [] }
  },
  computed: {
    filteredResults() { return this.searchResults.filter(...) }
  },
  methods: {
    search() { /* 搜索逻辑 */ }
  },
  watch: {
    keyword(val) { this.search() }
  }
}
</script>

<!-- Composition API：搜索功能聚合在一起 -->
<script setup>
const keyword = ref('')
const searchResults = ref([])

const filteredResults = computed(() => searchResults.value.filter(...))

watch(keyword, () => { search() })

function search() { /* 搜索逻辑 */ }
</script>
```

**第二层：逻辑复用（Mixin 三大痛点）**

```js
// Vue2 Mixin 的痛点
// mixins/validate.js
export default {
  data() { return { errors: {} } },
  methods: { validate() { /* ... */ } }
}

// 组件里用
import validateMixin from './validate.js'
import authMixin from './auth.js'       // 可能有同名方法
import i18nMixin from './i18n.js'       // 可能有同名属性

export default {
  mixins: [validateMixin, authMixin, i18nMixin],
  methods: {
    submit() {
      this.validate()  // ❌ 这个 validate 来自哪个 Mixin？要翻 3 个文件
    }
  }
}
```

```ts
// Vue3 Composable —— 显式导入，来源清晰
// composables/useValidate.ts
import { ref } from 'vue'

export function useValidate() {
  const errors = ref<Record<string, string>>({})
  function validate() { /* ... */ }
  return { errors, validate }
}

// composables/useAuth.ts
export function useAuth() {
  const user = ref(null)
  function login() { /* ... */ }
  return { user, login }
}
```

```vue
<!-- 组件里用 —— 来源一目了然 -->
<script setup>
import { useValidate } from './composables/useValidate'
import { useAuth } from './composables/useAuth'

// 解构出来，命名冲突可重命名
const { errors, validate } = useValidate()
const { user, login } = useAuth()

function submit() {
  validate()  // ✅ 明确来自 useValidate
}
</script>
```

Mixin 痛点总结：
| 痛点 | Mixin | Composable |
|------|-------|-----------|
| 命名冲突 | 多个 Mixin 同名直接覆盖 | 解构时可重命名 |
| 来源不透明 | `this.xxx` 不知道哪来的 | 显式 import |
| 类型推导差 | TS 无法推断 this 上的属性 | 返回值有完整类型 |

**第三层：工程化收益**
- **Tree-shaking**：没用到的 API 不打包（Options API 的 `this.xxx` 静态分析做不到）
- **TypeScript 一等公民**：ref/reactive/computed 都有完整类型推导
- **灵活组合**：Composables 可以嵌套，Mixin 只能扁平合并

```ts
// Composable 嵌套组合 —— Mixin 做不到
export function useUserPage() {
  const { users, filtered } = useUserList()
  const { page, pageSize, paginate } = usePagination(filtered)
  return { users: filtered, page, pageSize, paginate }
}
```

**面试加分说法：**
> "在 Vue2 项目中，一个复杂表单组件可能有 5 个 Mixin，模板里 `this.validate` 得翻 5 个文件才知道来源。Composition API 用 Composables 替代后，逻辑来源是显式 import 的，可追踪、可测试、可类型推导。"

## 2. ref 和 reactive 有什么区别？

### 核心回答

| | ref | reactive |
|---|---|---|
| 能包什么 | 基本类型 + 对象都可以 | 只能包对象 |
| 访问方式 | script 里 `.value`，模板自动解包 | 直接访问属性 |
| 解构行为 | 安全 | **丢失响应性**（需 toRefs） |
| 整体替换 | ✅ `x.value = newObj` | ❌ 不能替换 |
| 底层机制 | class 的 getter/setter + 内部自动调 reactive | Proxy 代理 |

### ref 示例

```ts
import { ref } from 'vue'

// 基本类型
const count = ref(0)
count.value++               // script 里必须 .value

// 对象也能包
const user = ref({ name: '张三', age: 25 })
user.value.name = '李四'     // ✅ 改属性，响应式
user.value = { name: '王五' } // ✅ 整体替换，也是响应式
```

### reactive 示例

```ts
import { reactive, toRefs } from 'vue'

const state = reactive({ name: '张三', age: 25 })
state.name = '李四'          // ✅ 直接改，不需要 .value

// ❌ 不能整体替换
state = { name: '王五' }     // 报错，const 不能重新赋值

// ❌ 解构丢失响应性
let { name } = state         // name 变成普通字符串，和 state 断开
name = '李四'                 // 视图不更新

// ✅ 用 toRefs 解构保持响应式
const { name } = toRefs(state)
name.value = '李四'           // 视图更新
```

### 模板中的区别

```vue
<template>
  <!-- ref 自动解包，不需要 .value -->
  <p>{{ count }}</p>          <!-- 等价于 count.value -->
  <p>{{ user.name }}</p>      <!-- 等价于 user.value.name -->

  <!-- reactive 直接用 -->
  <p>{{ state.name }}</p>     <!-- 直接 state.name -->
</template>

<script setup>
const count = ref(0)
const user = ref({ name: '张三' })
const state = reactive({ name: '张三' })
</script>
```

### ref 的结构图

```
user（ref 盒子）
  └── .value（拿到里面的对象）
        ├── .name  ← 直接改，响应式（不需要再 .value）
        └── .age   ← 直接改，响应式
```

### 为什么 reactive 解构会丢响应性

```ts
// 解构本质就是赋值
const state = reactive({ name: '张三' })
let { name } = state
// 等价于：let name = state.name
// name 拿到的是字符串 '张三' 本身，不是对 state.name 的引用
// JavaScript 赋值是复制值，不保留来源
```

### 实际开发怎么选

```ts
// ❌ 混用，心智负担大
const name = ref('张三')
const form = reactive({ phone: '138xxx' })

// ✅ 统一用 ref，简单一致
const name = ref('张三')
const form = ref({ phone: '138xxx' })
```

**面试加分说法：**
> "ref 是万能盒子，什么都能装，取值加 `.value`；reactive 只装对象，不能换盒子，解构会漏。团队主流做法是 ref 一把梭——统一心智模型，不用担心解构问题。"

## 3. Vue3 响应式 vs Vue2 响应式（Proxy vs defineProperty）

### 核心回答（4 个对比点）

**1. 无法检测属性的新增/删除**

```js
// Vue2
export default {
  data() {
    return { user: { name: '张三' } }
  },
  methods: {
    addAge() {
      this.user.age = 25       // ❌ 视图不更新
      this.$set(this.user, 'age', 25)  // ✅ Vue2 补救方法
    },
    removeName() {
      delete this.user.name    // ❌ 视图不更新
      this.$delete(this.user, 'name')  // ✅
    }
  }
}

// Vue3
const user = reactive({ name: '张三' })
user.age = 25          // ✅ 新增属性，Proxy 的 set trap 能捕获
delete user.name       // ✅ 删除属性，也触发更新
```

**2. 无法检测数组索引赋值和 length 修改**

```js
// Vue2
this.list[0] = '新值'       // ❌ 索引赋值
this.list.length = 0        // ❌ 修改 length

// Vue2 只能用变异方法（重写了 7 个数组方法）
this.list.splice(0, 1, '新值')   // ✅
this.$set(this.list, 0, '新值')  // ✅
this.list.push('新值')           // ✅ push/pop/splice/sort/reverse/shift/unshift

// Vue3
state.list[0] = '新值'      // ✅ Proxy 直接支持
state.list.length = 0       // ✅
```

**3. 初始化性能：递归遍历 vs 惰性代理**

```js
// Vue2：创建时遍历每个属性，逐个 defineProperty
// 嵌套越深，初始化越慢
data() {
  return {
    list: new Array(10000).fill({ ... })  // 10000 个对象每个属性都要劫持
  }
}

// Vue3：Proxy 代理整个对象 + 嵌套对象惰性代理（用到才代理）
const state = reactive({ list: [] })
// 初始化时不会遍历 list 里面的每一项
// 只有访问 state.list[0] 时，才会对 list[0] 做响应式包装
```

**4. Proxy 的局限**

- 不能代理基本类型 → 所以 ref 用 class 的 getter/setter
- IE 不支持 → Vue3 放弃 IE

### 对比图

```
Vue2 defineProperty              Vue3 Proxy
┌───────────────────────┐       ┌───────────────────────┐
│ 逐个属性装监控         │       │ 整个门口装一个门禁      │
│ ┌───┐ ┌───┐ ┌───┐    │       │ ┌─────────────────┐   │
│ │name│ │age│ │ ... │    │       │ │  整个对象        │   │
│ └───┘ └───┘ └───┘    │       │ │  新属性也能拦到   │   │
│ 新加的属性没监控 ❌    │       │ └─────────────────┘   │
│ 每个属性递归劫持 🐌   │       │ 惰性代理，按需触发 ⚡  │
└───────────────────────┘       └───────────────────────┘
```

**面试加分说法：**
> "Vue2 的 defineProperty 是在属性级别做拦截，所以新增属性和数组索引赋值检测不到。Vue3 的 Proxy 是在对象级别做拦截，所有操作都能捕获。而且嵌套对象是惰性代理——用到才包装，不用不浪费。"

## 4. watch 和 watchEffect 有什么区别？

### 核心回答

| | watch | watchEffect |
|---|---|---|
| 指定监听源 | 手动指定 | 自动收集依赖 |
| 新旧值 | 有 `(newVal, oldVal)` | 没有 |
| 默认执行 | 懒执行（值变了才跑） | 立即执行一次 |
| 精确控制 | 强 | 弱 |
| 适用场景 | 对比新旧值、精确监听 | 副作用（发请求、DOM 操作） |

### watch 示例

```ts
import { ref, watch } from 'vue'

const keyword = ref('')

// 基本用法：精确监听，能拿到新旧值
watch(keyword, (newVal, oldVal) => {
  console.log(`${oldVal} → ${newVal}`)
  fetchList(newVal)
})

// 监听多个源
const page = ref(1)
watch([keyword, page], ([newKw, newPg], [oldKw, oldPg]) => {
  fetchList(newKw, newPg)
})

// 监听 reactive 的某个属性 —— 必须用 getter
const state = reactive({ name: '张三', age: 25 })
watch(() => state.name, (newVal, oldVal) => {
  console.log(newVal, oldVal)
})
// ❌ watch(state.name, ...) 不行，传的是属性值不是响应式源

// 立即执行（等同 watchEffect 的立即执行）
watch(keyword, (val) => {
  fetchList(val)
}, { immediate: true })

// 深度监听
const form = ref({ user: { name: '' } })
watch(form, (newVal) => {
  console.log('表单变了', newVal)
}, { deep: true })
```

### watchEffect 示例

```ts
import { ref, watchEffect } from 'vue'

const keyword = ref('')

// 自动收集依赖：里面用了 keyword.value，自动监听 keyword
watchEffect(() => {
  console.log(keyword.value)  // 执行时自动收集 keyword 为依赖
  fetchList(keyword.value)
})

// 清理副作用（取消上一次请求）
watchEffect((onCleanup) => {
  const controller = new AbortController()

  fetch(`/api/list?q=${keyword.value}`, { signal: controller.signal })

  onCleanup(() => controller.abort())  // 下次执行前或组件卸载时调用
})
```

### watch 也能清理副作用

```ts
watch(keyword, (newVal, oldVal, onCleanup) => {
  const controller = new AbortController()
  fetch(`/api/list?q=${newVal}`, { signal: controller.signal })
  onCleanup(() => controller.abort())
})
```

### 混用完全没问题

```ts
// 同一组件里混用，各自独立
const keyword = ref('')
const page = ref(1)
const list = ref([])

// watch：需要对比新旧值
watch(keyword, (newVal, oldVal) => {
  if (newVal !== oldVal) page.value = 1
})

// watchEffect：纯副作用，自动收集
watchEffect(() => {
  fetch(`/api/list?q=${keyword.value}&page=${page.value}`)
    .then(res => res.json())
    .then(data => list.value = data)
})
```

**面试加分说法：**
> "需要新旧值对比或精确控制触发条件用 watch；纯副作用用 watchEffect 更简洁。但团队协作时 watch 可读性更好——一眼看出监听了什么。"

## 5. Vue3 生命周期钩子有什么变化？

### 核心回答

| Vue2 | Vue3 Composition API | 变化说明 |
|------|---------------------|---------|
| beforeCreate | setup() 开始 | 被 setup 替代 |
| created | setup() 内直接写 | 被 setup 替代 |
| beforeMount | onBeforeMount() | 加 on 前缀 |
| mounted | onMounted() | 加 on 前缀 |
| beforeUpdate | onBeforeUpdate() | 加 on 前缀 |
| updated | onUpdated() | 加 on 前缀 |
| beforeDestroy | onBeforeUnmount() | **改名**：destroy → unmount |
| destroyed | onUnmounted() | **改名**：destroy → unmount |
| (无) | onRenderTracked() | 新增调试钩子 |
| (无) | onRenderTriggered() | 新增调试钩子 |

### beforeCreate / created 的替代

```ts
// Vue2
export default {
  beforeCreate() { /* 初始化逻辑 */ },
  created() { this.fetchData() },
}

// Vue3 <script setup>
<script setup>
// 这里的代码 = created 阶段执行，不需要钩子
fetchData()
</script>
```

### 所有钩子的用法

```vue
<script setup>
import {
  onBeforeMount,
  onMounted,
  onBeforeUpdate,
  onUpdated,
  onBeforeUnmount,
  onUnmounted,
} from 'vue'

// setup 内直接写 = created
console.log('created 阶段')

onBeforeMount(() => {
  console.log('DOM 挂载前')
})

onMounted(() => {
  console.log('DOM 挂载后，可以操作 DOM')
  // 常用：发请求、初始化第三方库、添加事件监听
})

onBeforeUpdate(() => {
  console.log('数据变化，DOM 更新前')
})

onUpdated(() => {
  console.log('DOM 更新后')
})

onBeforeUnmount(() => {
  console.log('组件卸载前')
  // 清理定时器、取消请求、移除事件监听
})

onUnmounted(() => {
  console.log('组件已卸载')
})
</script>
```

### 卸载时的清理（常见面试追问）

```vue
<script setup>
import { ref, onMounted, onBeforeUnmount } from 'vue'

const timer = ref(null)

onMounted(() => {
  timer.value = setInterval(() => {
    console.log('轮询中...')
  }, 3000)
})

onBeforeUnmount(() => {
  clearInterval(timer.value)  // 必须清理，否则内存泄漏
})
</script>
```

**面试加分说法：**
> "setup 本身等价于 beforeCreate + created，所以这两个钩子不再需要。其他钩子加 on 前缀，destroyed 改名 unmounted 更准确——组件不是被销毁，是从 DOM 树上卸载。"

## 6. Pinia 和 Vuex 有什么区别？

### 核心回答

| | Vuex | Pinia |
|---|---|---|
| mutations | 有，必须同步 | **没有**，砍了 |
| actions | 只能异步（约定） | 同步异步统一 |
| 调用方式 | commit / dispatch | 直接调用函数 |
| TS 支持 | 差（需要手写声明） | 原生支持 |
| 模块化 | modules + 命名空间 | 多 store 独立导入 |
| 体积 | ~16KB | ~1KB |
| DevTools | 支持 | 支持 |

### Vuex 的痛点：样板代码

```ts
// Vuex —— 改一个值要写两层（mutations + actions）
const store = {
  state: { count: 0 },
  mutations: {
    increment(state) { state.count++ }           // 同步，就一行赋值
    setCount(state, val) { state.count = val }   // 同步，还是一行赋值
  },
  actions: {
    incrementAsync({ commit }) {
      commit('increment')        // action 里就是转发一下
    },
    async fetchCount({ commit }) {
      const res = await api.getCount()
      commit('setCount', res.data)  // 异步结果还得 commit
    }
  }
}

// 组件里调用方式还不一样
this.$store.commit('increment')              // 同步用 commit
this.$store.dispatch('fetchCount')           // 异步用 dispatch
```

99% 的 mutations 就是 `state.xxx = payload`，action 就是转发一下。两层代码干一行赋值的活，这就是"样板代码"。

### Pinia 的写法：统一简洁

```ts
// stores/counter.ts
import { defineStore } from 'pinia'

export const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0, list: [] }),

  getters: {
    doubleCount: (state) => state.count * 2,
  },

  actions: {
    // 同步 action —— 直接改 state，不需要 mutations
    increment() {
      this.count++              // 直接 this 赋值
    },

    // 异步 action —— 和同步用同一个函数，不用 commit
    async fetchCount() {
      const res = await api.getCount()
      this.count = res.data     // 直接赋值
    }
  }
})

// 组件里调用 —— 统一方式，没有 commit/dispatch
const counter = useCounterStore()
counter.increment()          // 同步
counter.fetchCount()         // 异步
```

### Pinia 的 Setup Store 语法

```ts
// 和 <script setup> 风格一致
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useCounterStore = defineStore('counter', () => {
  const count = ref(0)
  const doubleCount = computed(() => count.value * 2)

  function increment() { count.value++ }

  async function fetchCount() {
    const res = await api.getCount()
    count.value = res.data
  }

  return { count, doubleCount, increment, fetchCount }
})
```

### 多 store 不需要 modules

```ts
// Vuex —— 嵌套命名空间
this.$store.dispatch('user/login')
this.$store.state.user.name
this.$store.state.cart.items

// Pinia —— 各自独立，按需导入
const user = useUserStore()
const cart = useCartStore()

user.login()        // 直接调用
user.name           // 直接访问
cart.items
```

### mutations 为什么被砍掉

Vuex 当年设计 mutations 必须同步，是因为 DevTools 靠记录每次 commit 快照做调试。异步 mutation 会导致快照顺序混乱。

但现代 DevTools 已经能追踪 `async/await` 的完整调用栈，不需要靠"同步 mutations"保证可追踪。所以 Pinia 大胆砍掉了。

```
2016 年 Vuex 设计时：DevTools 追踪不了异步 → mutations 必须同步
2020 年 Pinia 设计时：DevTools 已经能追踪异步 → mutations 没必要存在了
```

### Vue DevTools 是什么

浏览器插件（Chrome/Firefox），Vue 应用的调试工具。按 F12 打开开发者工具，顶部 tab 栏会出现 "Vue" 选项卡。

核心能力：
- **组件树**：页面由哪些组件组成，props 传了什么
- **状态查看**：ref/reactive 的实时值，可以直接在面板里改
- **时间旅行**：每次状态变化都有快照，可以回退到任意一步
- **路由和状态管理**：Vue Router 和 Pinia/Vuex 的变化也能追踪

```
简单理解：DevTools = Vue 应用的 X 光机
能看到组件内部长什么样、数据怎么变的、哪一步出了问题
```

**面试加分说法：**
> "Pinia 砍掉 mutations 是因为它们 99% 就是 `state.xxx = payload` 的样板代码。现代 DevTools 已经能追踪 async/await，不需要靠同步 mutations 保证可调试性。加上原生 TS 支持、1KB 体积、无嵌套模块，Pinia 是 Vuex 的全面替代。"

## 7. Vue3 为什么比 Vue2 快？（编译优化）

### 核心回答

Vue3 的性能提升不是运行时 diff 算法变了，而是**编译时**就做好了优化标记。

| 优化手段 | 做了什么 | 效果 |
|---------|---------|------|
| 静态提升 | 静态节点只创建一次 | 避免重复创建 |
| PatchFlags | 标记动态节点的变化类型 | diff 只检查标记部分 |
| Block Tree | 模板按动态节点分块 | 跳过静态节点 |
| Tree-shaking | ES Module 按需导入 | 没用到的功能不打包 |

### 优化 1：静态提升（Static Hoisting）

```vue
<template>
  <div>
    <h1>固定标题</h1>
    <p>{{ message }}</p>
  </div>
</template>
```

```js
// Vue2 编译结果：每次更新都重新创建所有节点
render() {
  return h('div', [
    h('h1', '固定标题'),    // 每次都 new
    h('p', this.message)
  ])
}

// Vue3 编译结果：静态节点只创建一次，提升到外面
const hoisted = h('h1', '固定标题')  // 提升到模块顶层，只创建一次

render() {
  return h('div', [
    hoisted,                // 直接复用
    h('p', message.value)
  ])
}
```

类比：Vue2 每次搬家都重新买家具，Vue3 把固定家具钉死在墙上，搬的时候只搬会动的东西。

### 优化 2：PatchFlags（补丁标记）

```vue
<template>
  <div :class="activeClass" id="fixed-id">
    <span>{{ text }}</span>
  </div>
</template>
```

```js
// Vue2 —— diff 时对比所有属性（tag/text/props/class/style...）
if (oldNode.tag !== newNode.tag) { /* ... */ }
if (oldNode.text !== newNode.text) { /* ... */ }
if (oldNode.props !== newNode.props) { /* ... */ }
// 每个属性都要比

// Vue3 —— 编译器标记了"哪里会变"
h('span', text.value, PatchFlags.TEXT)  // 标记：只有文本会变

// diff 时只检查文本，跳过 class/style/props 等检查
// PatchFlags 的值代表不同类型：
// PatchFlags.TEXT   = 1  只检查文本
// PatchFlags.CLASS  = 2  只检查 class
// PatchFlags.STYLE  = 4  只检查 style
// PatchFlags.PROPS  = 8  只检查非 class/style 的属性
```

类比：Vue2 是快递员挨家挨户敲门问"有包裹吗"，Vue3 是包裹上贴了标签说"只送 3 楼"，直接跳过其他楼层。

### 优化 3：Block Tree（块级树）

```vue
<template>
  <div>
    <h1>固定标题</h1>          <!-- 静态，永远不变 -->
    <p class="desc">说明文字</p>  <!-- 静态，永远不变 -->
    <span>{{ dynamic }}</span>  <!-- 动态 -->
    <ul>
      <li v-for="item in list">{{ item }}</li>  <!-- 动态 -->
    </ul>
  </div>
</template>
```

```
Vue3 编译后形成 Block：
Block (div)
  ├── h1   → 跳过（静态）
  ├── p    → 跳过（静态）
  ├── span → 检查（标记了 TEXT_PATCH_FLAG）
  └── ul   → 检查（动态子节点）
```

diff 时只对比 Block 里标记为动态的节点，静态的完全跳过。

### 优化 4：Tree-shaking

```ts
// Vue2 —— 全量导入，用不用都打包
import Vue from 'vue'
// Vue 对象上挂了所有功能：nextTick、set、delete、mixin、filter...
// 你只用 ref，但 transition、keep-alive、v-model 的代码全打进来了

// Vue3 —— 按需导入，没用到的不会打包
import { ref, computed, watch } from 'vue'
// 只有这三个被打包，其余的 Tree-shaking 掉
// transition 没用？不打包
// keep-alive 没用？不打包
```

Vue3 用 ES Module 的静态 import，打包工具能分析出哪些没被使用并删除。Vue2 的全局 Vue 对象做不到。

### 对比图

```
Vue2 编译                    Vue3 编译
┌──────────────────────┐    ┌──────────────────────────┐
│ 全部重新创建           │    │ 静态节点只创建一次（提升） │
│ 全部重新对比           │    │ 只对比标记了的动态节点     │
│                       │    │ (PatchFlags)             │
│ 全量打包              │    │ 没用的功能不打包           │
│                       │    │ (Tree-shaking)           │
│ 搬家全搬              │    │ 只搬会动的东西            │
└──────────────────────┘    └──────────────────────────┘
```

### 关键追问：diff 算法变了吗？

没有。Vue3 的 diff 算法本质上还是双端对比，和 Vue2 类似。性能提升来自编译器标记**减少了 diff 的范围**，不是算法本身更快。

**面试加分说法：**
> "Vue3 的性能提升主要来自编译时优化。编译器标记了静态节点并提升到渲染函数外部避免重复创建；通过 PatchFlags 告诉 diff 算法只检查动态部分；配合 ES Module 实现 Tree-shaking 去掉没用到的功能。本质上是用编译时间换运行时性能。"

## 复习速查表

```
Composable  = 函数，useXxx，显式 import，替代 Mixin
ref         = 万能盒子，.value 访问，什么都能装，解构安全
reactive    = Proxy 对象，直接访问属性，解构丢响应性（要 toRefs）
Proxy       = 代理整个对象，新增/删除/数组索引都能检测，惰性代理
watch       = 精确监听，有新旧值，默认懒执行
watchEffect = 自动收集，无旧值，立即执行，适合副作用
生命周期     = 加 on 前缀，destroyed→unmounted，created→setup 内直接写
Pinia       = 砍掉 mutations，同步异步统一 actions，this 直接赋值，~1KB
DevTools    = 浏览器插件，Vue 应用的 X 光机，组件树 + 状态快照 + 时间旅行
编译优化     = 静态提升 + PatchFlags + Block Tree + Tree-shaking，用编译时间换运行时性能
```
