# RAG项目架构设计

更新时间：2026-05-07

## 项目定位

`rag-docs-assistant` 是一个面向专业资料场景的 AI 知识库问答系统，目标不是做纯聊天机器人，而是把“文档入库 -> 检索 -> 回答 -> 来源追溯 -> 图谱增强”串成一个完整可演示闭环。

---

## 总体结构

项目按三个工作区组织：

1. `chat`
   对话问答、来源引用、历史对话恢复

2. `data`
   知识库管理、文档上传、文档列表和切片统计

3. `graph`
   知识图谱概览、搜索、节点详情、收藏

技术上分为四层：

1. 页面与组件层
2. API Route 业务层
3. 文档处理 / 检索 / 图谱服务层
4. 本地持久化与向量存储层

---

## 核心链路

### 1. 文档入库链路

```text
用户上传文件
-> 校验知识库、文件类型、大小、重名
-> 按文件类型解析为纯文本
-> 按标题和固定长度切片
-> 调用 embedding-3 生成向量
-> 写入向量存储（FileStore / ChromaStore）
-> 保存文件和文档元数据
-> 异步抽取实体关系，写入图谱
```

关键点：

- 支持 `.txt`、`.md`、`.pdf`、`.docx`、`.xlsx`
- 当前切片参数：`chunkSize=1000`、`overlap=100`
- 每个片段保留 `filename`、`heading`、`chunkIndex` 元数据
- 图谱抽取异步执行，不阻塞入库主链路

### 2. 问答检索链路

```text
用户提问
-> 读取当前 kbId
-> 构造 searchQuery（带最近上下文）
-> 确定检索范围
-> 生成 query embedding
-> 执行相似度检索 / 混合检索
-> 召回 topK 相关片段
-> 组装 system prompt 和上下文
-> 调用 glm-4-flash 流式生成回答
-> 返回答案和 sources
```

关键点：

- 单知识库模式：只检索当前知识库
- 全部模式：当前是跨所有知识库统一检索
- FileStore 模式下支持向量检索 + 关键词检索 + RRF 融合
- `sources` 用于来源追溯和排查检索质量

### 3. 图谱增强链路

```text
上传成功
-> 创建文档节点
-> 调用 LLM 抽取实体和关系
-> 存到 graphology 图结构
-> 图谱页做概览、搜索、节点详情和邻域扩展
```

边界：

- 当前图谱主要用于可视化和浏览
- 还没有进入问答检索主链路
- 还不能称为完整 GraphRAG

## 关键模块划分

### 前端

- `src/app/(platform)/layout.tsx`
  管理平台布局、知识库选择和左侧会话列表

- `src/components/chat/*`
  负责问答输入、消息流展示、来源卡片

- `src/components/data/*`
  负责知识库、文档列表、上传交互

- `src/components/graph/*`
  负责图谱画布、节点详情、搜索与收藏

### 后端 API

- `/api/kb`
  知识库创建、删除、文档查询、上传

- `/api/chat`
  RAG 对话主链路，返回 SSE 流式回答

- `/api/chat/history`
  对话列表和单个会话恢复

- `/api/graph`
  图谱概览、搜索、收藏、邻域详情

### 服务层

- `doc-parser.ts`
  多格式文档解析

- `chunker.ts`
  文本切片

- `embedding.ts`
  向量化接口

- `vector-store/*`
  向量存储抽象

- `graph-store.ts`
  图谱存取

- `db.ts`
  本地业务元数据持久化

## 数据存储设计

当前版本采用本地文件持久化，主要目的是低成本演示和快速闭环：

- `data/db.json`
  知识库、文档、对话和消息元数据

- `data/vectors.json`
  FileStore 模式下的向量数据

- `data/graph.json`
  图谱结构数据

- `data/uploads/`
  原始上传文件

- `data/app.log`
  上传、检索、问答等关键日志

这样做的优点：

- 启动简单
- 无额外数据库依赖
- 适合个人项目和本地演示

局限：

- 不适合多人并发
- 存在写覆盖和锁竞争风险
- 不适合大规模向量检索

## 关键设计取舍

### 1. 单知识库 + 全部知识库并存

- 单知识库：强调检索精度
- 全部知识库：强调跨库覆盖

这是“精度”和“范围”的平衡。

### 2. 返回 Sources

不是装饰性功能，而是：

- 让答案可追溯
- 让用户能回看原文
- 让调试时区分检索层和生成层问题

### 3. FileStore / ChromaStore 抽象

- 当前优先低成本落地
- 未来预留扩展空间
- 不把上层问答链路写死在单一存储实现上

### 4. 图谱异步执行

- 保护上传主链路
- 保证文档先可检索、可问答
- 增强能力失败不拖垮主流程

---

## 当前限制

1. 全部模式还没有 AI 路由
2. 图谱未接入问答主链路
3. 业务元数据和默认向量存储仍为本地 JSON / FileStore
4. 无用户权限、多租户和生产级并发保障
5. 删除单个文档时图谱节点清理还未闭环

---

## 后续演进方向

1. 全部模式增加 AI 路由
   先根据知识库名称、简介和用户问题输出候选库及置信度，再缩小检索范围

2. 存储升级
   业务元数据迁移到 SQLite / PostgreSQL，向量迁移到 Chroma / pgvector

3. 图谱状态闭环
   增加图谱抽取状态展示、失败原因和重试入口

4. 图谱增强检索
   只有图谱真正进入问答链路后，才考虑往 GraphRAG 方向继续演进
