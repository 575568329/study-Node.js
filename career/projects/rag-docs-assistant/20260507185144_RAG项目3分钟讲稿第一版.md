## 3分钟完整版

我做的这个项目，本质上是一个面向专业资料检索场景的 AI 知识库问答系统，主要解决业务文档分散、查找效率低、知识复用成本高的问题。用户可以把 PDF、Word、Excel、Markdown 这类资料上传到知识库中，系统会基于文档内容做检索增强问答，让用户用自然语言快速获取答案，并看到答案对应的来源片段。

这个项目的核心链路可以分成入库和问答两段。入库时，系统会先解析用户上传的文档内容，再按固定规则切片，并调用 embedding 模型把文本片段转成向量，写入向量库。同时，文件路径、文件名、所属知识库等业务信息会保存到本地业务存储里。当前项目全程使用 GLM 生态，Embedding 使用 `embedding-3`，问答模型使用 `glm-4-flash`，并通过 AI SDK 实现流式回答。

问答时，系统会先根据当前选择的知识库确定检索范围。如果用户选择的是单个知识库，就只在该知识库内检索；如果用户选择的是“全部”，当前版本会跨所有知识库统一检索。后端会把用户问题和最近上下文拼成 `searchQuery`，生成查询向量后，到目标知识库集合里做检索，召回最相关的若干文本片段，再把这些片段和用户问题一起交给大模型生成最终答案。最后除了返回 answer，还会返回 sources，方便前端展示答案引用了哪个知识库、哪个文件片段。

相比直接把整份文档交给大模型，这种方案的优势比较明显。第一是成本更可控，因为只把最相关的片段交给模型，不需要每次都消耗大量 token。第二是回答更聚焦，无关内容更少，模型不容易被噪音干扰。第三是答案具备可追溯性，用户可以回到原始文件片段验证上下文，而不是只能看到一个黑盒回答。随着文档规模增加，这种“先检索、再生成”的方式也比直接全文喂模型更容易扩展。

在设计上，我做了几个比较关键的取舍。第一，项目同时支持单知识库和全部知识库两种模式，前者更强调检索精度，后者更强调跨领域覆盖，让用户自己决定检索范围。第二，我在回答结果里保留了 sources，不只是为了展示效果，而是为了增强答案可信度和后续排查能力。第三，向量存储层做了抽象，当前支持本地 FileStore 和可切换的 ChromaStore，小规模演示可以走轻量方案，后续扩展时也保留了升级空间。第四，知识图谱抽取放在上传成功后的异步链路里，不阻塞文档入库主流程，保证即使图谱抽取失败，问答主链路也能先正常工作。

如果后续继续升级，我会优先补“全部模式”的 AI 路由。也就是当用户没有指定知识库时，先让模型根据知识库名称、简介和用户问题输出候选知识库及置信度，再缩小检索范围，最后再执行向量检索和回答生成。这样可以降低跨库检索噪音，提高召回精度和响应效率。

## 1分钟压缩版

这个项目是一个面向专业资料场景的 AI 知识库问答系统，解决的是文档分散、查找效率低和知识难复用的问题。用户上传 PDF、Word、Excel 等文档后，系统会先解析文本、切片、做 embedding，并把文本片段和向量写入向量库。用户提问时，后端会根据当前知识库范围召回最相关的几个片段，再把问题和片段一起交给大模型生成答案，同时返回 sources 做来源追溯。这个项目的重点不是简单接一个大模型接口，而是把文档入库、检索、流式回答和来源引用串成了一个完整闭环。

这是一个 AI 知识库问答系统，主要解决专业资料分散、查找效率低的问题。用户上传文档后，系统会做文本解析、切片和向量化存储；提问时先检索相关片段，再交给大模型生成答案，并返回来源引用。我的重点工作是把知识库管理、RAG 检索链路、流式回答和可追溯性做成一个完整可演示的闭环。

## 讲的时候容易说错的点

1. 不要把“后续升级项”讲成“当前已完成能力”
   当前“全部模式”是跨所有知识库统一检索，还没有正式接入 AI 路由。

2. 不要把业务存储说成 SQL
   当前项目主要是本地 JSON 持久化，SQL / PostgreSQL 是后续演进方向。

3. 不要把问答模型说错
   当前代码里问答模型是 `glm-4-flash`，Embedding 是 `embedding-3`。

4. 不要把文档解析说成“用了几个插件”
   更准确的说法是：
   - PDF 用 `pdfjs-dist`
   - DOCX 用 `mammoth`
   - XLSX 用 `ExcelJS`

5. 不要只讲上传链路，忘了问答链路
   面试讲 RAG 项目时，必须同时讲“入库”和“问答”。
