## README 推荐结构

### 1. 项目简介

建议开头保留一句话定位，但加上更明确的业务价值描述：

```text
一个面向专业资料场景的 AI 知识库问答系统，支持多格式文档入库、检索增强问答、来源引用和知识图谱展示。
```

目标：

- 让访问者 10 秒内知道项目做什么
- 让面试官 30 秒内知道这个项目不只是“接了个大模型”

### 2. 核心能力

建议改成更像成果清单，而不是平铺功能点：

1. 多知识库管理和范围切换
2. 多格式文档解析、切片、向量化入库
3. 单知识库 / 全部知识库检索问答
4. `sources` 来源追溯
5. 混合检索（向量 + 关键词 + RRF）
6. 知识图谱异步抽取与展示

### 3. 演示流程

这是当前 README 最该补的一节。

建议加：

1. 创建知识库
2. 上传 1 到 2 份示例文档
3. 在单知识库模式下提问
4. 在全部知识库模式下提问
5. 查看来源引用
6. 切到图谱页查看实体关系

### 4. 架构说明

不要画太复杂，README 里放一版简化文字链路即可：

```text
文档上传 -> 文本解析 -> 切片 -> Embedding -> 向量存储
用户提问 -> 检索范围确定 -> 相似度检索 -> Prompt 组装 -> LLM 流式回答 -> Sources 返回
```

### 5. 当前限制

这一节非常重要，能防止写得过满。

建议明确写：

- 当前业务元数据和默认向量存储为本地 JSON / FileStore，适合演示和单机使用
- 全部知识库模式当前是统一检索，还未接入 AI 路由
- 图谱抽取为异步增强链路，失败不影响问答主流程
- 当前无用户权限和多租户隔离

### 6. 演进方向

建议写成 3 条以内：

1. 全部模式增加 AI 路由，先缩小知识库范围再检索
2. 业务元数据迁移到 SQLite / PostgreSQL，向量存储迁移到 Chroma / pgvector
3. 图谱抽取补状态展示和重试机制

## README 中建议新增的小节

### 为什么不用“整篇文档直接喂模型”

这节可以非常短，但很加分：

- 降低 token 成本
- 提高回答聚焦度
- 避免上下文窗口限制
- 支持来源追溯

### 为什么返回 Sources

- 提高用户信任
- 方便回看原文
- 方便排查检索层和生成层问题

## 直接可放进 README 的项目亮点文案

```text
- 支持 PDF / Word / Excel / Markdown 多格式文档解析和统一入库
- 基于向量检索、关键词检索和 RRF 融合排序提升召回效果
- 使用 AI SDK 实现流式问答，并通过 Sources 返回来源引用
- 支持单知识库精确问答和全部知识库跨库检索
- 知识图谱抽取采用异步增强链路，不阻塞主上传流程
```
