## 一、离职与求职动机

### 1. 为什么离开讯飞？

**答题要点**：
- **客观原因**：公司面临业务调整和裁员，约1个月后我所在的项目组会解散
- **主动选择**：与其等到被动裁员，不如主动寻找更匹配我职业规划的机会
- **不是个人问题**：项目交付顺利，上线成功，和团队协作也很好
- **职业规划**：我希望找一个能深入AI Agent方向、有技术成长空间的岗位

**回答示例**：
"当前公司面临业务调整，我所在的澳门项目组大概1个月后会解散。项目本身已经顺利上线，我的工作交付也没有问题。与其等到被动裁员，我选择主动寻找更匹配我职业发展的机会。这段时间我一直在向AI全栈方向转型，自研了一套RAG系统并已上线，希望能找到一个能深入AI Agent方向、有技术成长空间的岗位。"

### 2. 为什么要转全栈/AI方向？

**答题要点**：

- **实践验证**：我自研的RAG系统已经跑通全链路，证明我有全栈交付能力
- **职业规划**：不只是写页面，而是能从0到1设计和落地AI产品

**回答示例**：
"我一直在思考前端工程师的职业天花板在哪。纯前端的竞争越来越激烈，而AI应用是当前最有潜力的方向。我有6年前端复杂业务经验，补强Node.js后端和AI链路后，能做到从需求设计、架构决策到上线验收的完整闭环。我自研的RAG系统已经跑通了文档上传、向量检索、流式问答、知识图谱的全链路，证明我不只是学了理论，而是能真正交付产品。"

## 二、优势与不足

### 4. 你最大的优势是什么？

**答题要点**：
- **实践能力强**：不只是学理论，RAG项目从0到1上线证明我能落地
- **学习能力快**：6年前端经验，1年内补齐Node.js后端和AI链路
- **架构思维**：讯飞项目的i18n双语言体系、三层组件设计都是我主导的
- **工具善用**：深度使用Claude Code/Codex提升效率，但保持对质量的把控

**回答示例**：
"我最大的优势是实践能力强。我不只是学了LangChain/LangGraph的API，而是真正做出了一套可演示、可上线的RAG系统。我有6年前端复杂业务经验，在讯飞项目中设计了i18n双语言决策体系和三层组件架构，证明我有架构思维。同时我善于用工具提效，深度使用Claude Code和Codex，但方案判断、代码审查和业务验证都由我把控。"

### 5. 你最大的不足是什么？

**答题要点**：
- **真实的不足**：选一个真实但不致命的点
- **改进措施**：说明你正在如何弥补
- **不要说的**：不要说"没有不足""太追求完美"这种假话

**三个可选方向**：

**方向1：后端经验相对薄弱**
"我的后端经验相对前端来说还不够深。虽然我的RAG项目用Next.js API Route跑通了全链路，但在高并发、分布式系统、数据库优化这些方面还需要继续学习。我现在的补强方式是：一边看Node.js/Next.js的最佳实践文档，一边把RAG项目的数据存储从本地JSON迁移到PostgreSQL+Chroma，在实践中积累经验。"

**方向2：AI算法理论深度不够**
"我在AI应用工程这块实践比较多，但算法理论深度还不够。比如向量检索的底层原理（HNSW、IVF）、Embedding模型的训练细节，我现在还停留在应用层面。我的补强方式是：在做项目的同时，阅读相关论文和技术博客，理解为什么这样设计、有哪些trade-off。我不追求成为算法专家，但希望理解得足够深，能在技术选型时做出正确判断。"

**方向3：大型团队协作经验不足**
"我在地大和讯飞的团队规模都不算很大（前端3-4人），缺少在大型团队（10人+前端）中协作的经验。大团队的代码规范、分支管理、Code Review流程可能更复杂。我的补强方式是：主动学习大厂的工程化实践（比如阿里的前端规范、字节的Monorepo实践），并在后续工作中快速适应团队流程。"

**推荐方向1**（最安全）：后端经验不足是全栈转型的自然短板，不会被质疑能力，反而显得诚实。

## 三、项目与技术

### 6. 最有挑战的项目是哪个？为什么？

- **选择讯飞澳门项目**（技术挑战 + 架构设计 + 团队协作）
- **挑战点**：i18n双语言决策、遗留系统改造、系统级风险隔离
- **如何克服**：方案设计 + 代码实现 + 持续优化
- **收获**：架构能力、工程化能力、AI协作能力

**回答示例**：
"最有挑战的是讯飞澳门项目。挑战主要有三点：第一是i18n双语言决策体系，工作室语言和页面语言必须并存，这不是简单的界面翻译；第二是5个遗留系统的技术债很重，代码风格不统一、组件重复开发、子项目互相依赖；第三是作为前端负责人，我要协调多人协作、做代码审查、把控上线质量。我通过设计resolveBizLocale()语言决策方案、开发i18n-check卡口脚本、沉淀三层组件架构，最终完成270+提交、900+文件变更，支撑澳门4语言上线。这个项目让我在架构设计、工程化能力、AI协作方面都有很大提升。"

### 7. 最有成就感的项目是哪个？

**答题要点**：
- **选择RAG项目**（从0到1 + 全栈闭环 + 技术转型证明）
- **成就点**：自己设计、自己实现、自己上线
- **技术亮点**：不只是调API，而是完整的产品闭环
- **职业意义**：证明我能从前端转向全栈AI

**回答示例**：
"最有成就感的是我的RAG项目。这是我从0到1设计、实现、上线的完整作品。它不只是跟着教程调LangChain的API，而是真正解决了文档检索和知识复用的问题，有完整的入库、检索、流式问答、来源引用闭环。我在做这个项目时，前端用Next.js、后端用API Route、AI链路用LangChain/LangGraph，第一次体验到全栈交付的成就感。这个项目也是我职业转型的证明——我不只是说要转全栈AI，而是真的做出来了。"

### 8. 遇到过最大的技术难题是什么？怎么解决的？

**答题要点**：
- **选择具体的技术问题**（不要泛泛而谈）
- **问题描述**：是什么问题、为什么难
- **解决过程**：尝试了哪些方案、最终怎么解决
- **经验总结**：学到了什么

**三个可选案例**：

**案例1：GIS项目十万级监测数据渲染卡顿**
"在GIS项目中，驾驶舱要展示十万级监测数据，一次性渲染会导致浏览器主线程阻塞、页面卡死。我一开始尝试用虚拟滚动，但监测点是分布在地图上的，不是列表，虚拟滚动不适用。后来我用了两个方案组合：第一是分级加载，省级只显示200-300个重点监测点，点击市县再加载详细数据；第二是显示时序控制，用requestAnimationFrame分批渲染，每帧100个点，逐渐铺满地图。这两个方案让首页加载提升约50%，用户体验明显改善。这次经验让我理解了前端性能优化不只是代码层面，更重要的是策略设计。"

**案例2：讯飞项目i18n基线增量策略设计**
"讯飞项目有32个语言文件，存量翻译问题有几百条。如果用传统的卡口脚本，一次性拦截所有问题，会导致无法提交代码。但如果不拦截，新增问题会越来越多。我设计了基线增量策略：首次运行记录当前所有问题为baseline，后续提交只拦截新增问题。这样既不阻塞历史遗留问题，又能保证新代码不引入新的翻译漏洞。实现时我用Claude Code生成初版脚本，我定义拦截规则，AI生成AST遍历和diff逻辑。这次经验让我学会如何在约束条件下设计可落地的工程方案。"

**案例3：RAG项目向量检索召回率低**
"RAG项目上线后，用户反馈有些问题明明文档里有答案，但系统回答不出来。我排查发现是向量检索的召回率低——用户问'如何配置环境变量'，但文档里写的是'环境变量设置方法'，语义相似但关键词不同，向量检索没召回。我加了混合检索（向量相似度+关键词），用RRF算法融合两路结果，召回率从60%提升到85%。这次经验让我理解了RAG不只是技术堆砌，更重要的是理解业务场景、优化召回策略。"

**推荐案例2**（最能体现架构思维和工程化能力）

### 9. 如何学习新技术？

**答题要点**：
- **学习路径**：理论 → 实践 → 总结
- **具体方法**：文档、项目、复盘
- **学习速度**：举例证明

**回答示例**：
"我学习新技术的路径是：先看官方文档理解核心概念，再做一个小demo验证理解，最后在真实项目中应用并总结经验。

以LangChain为例：我先看官方文档理解RAG Pipeline（加载、切片、向量化、检索、生成），然后做了一个最小demo跑通流程，最后在RAG项目中用LangChain.js实现完整链路，并在实践中优化召回策略、补充来源引用、加入知识图谱。

这个过程中我会记录学习笔记（在study-notes目录下），整理易错点和最佳实践，方便后续复习。我从开始学Node.js到完成RAG项目上线，大概用了1年时间，证明我的学习速度是比较快的。"

### 10. 如何看待AI辅助开发？

**答题要点**：
- **工具定位**：AI是助手，不是替代
- **使用边界**：什么场景用、什么场景不用
- **能力证明**：我仍然具备核心技术能力

**回答示例**：
"我认为AI辅助开发是提升效率的重要工具，但不是替代工程师的万能钥匙。

我深度使用Claude Code和Cursor，但有明确的使用边界：方案设计、架构决策、核心业务逻辑由我负责，AI主要用在代码生成、重复性改造、回归检查。我会明确告诉AI要改什么、不能动什么，生成的代码我都会逐行review，确保符合项目规范和业务语义。

举个例子：讯飞项目的i18n双语言决策架构是我设计的，resolveBizLocale()的判断逻辑是我定义的，AI只是帮我生成了具体的实现代码。如果我不具备架构设计能力，AI再强也生成不出正确的方案。

所以我的定位是：AI是我的代码助手，让我从重复劳动中解放出来，专注在更高价值的架构和业务决策上。"

## 四、团队与协作

### 11. 如何处理团队冲突？

**答题要点**：
- **冲突类型**：技术分歧、任务分配、进度压力
- **处理原则**：事实 + 目标对齐 + 妥协
- **举例说明**

**回答示例**：
"我遇到过技术方案分歧。比如讯飞项目中，有同事建议把语言文件全部合并成一个大JSON，方便管理。我认为应该拆分成多个文件，避免多人协作冲突。我的处理方式是：先列举两种方案的利弊（合并的优点是文件少，缺点是协作冲突；拆分的优点是协作友好，缺点是文件多），然后用数据说话（过去一个月因为语言文件冲突导致的重复工作时间），最后达成一致：拆分文件，用webpack的require.context自动加载。

我的原则是：用事实和数据说话，而不是凭感觉争论；目标对齐在团队效率和项目质量，而不是个人偏好；必要时适当妥协，尊重团队决策。"

### 12. 如何做代码审查？

**答题要点**：
- **审查重点**：业务逻辑 > 代码规范 > 性能优化
- **审查方式**：Checklist + 本地验证
- **反馈方式**：具体建议 + 正面鼓励

**回答示例**：
"我做代码审查的重点是：业务逻辑正确性 > 代码规范 > 性能优化。

业务逻辑这块，我会重点看：语言切换是否正确、数据隔离是否到位、边界场景是否处理。代码规范这块，我会看变量命名、函数拆分、注释完整性。性能优化这块，我会看是否有循环中的不必要请求、大列表是否做了虚拟滚动。

审查方式上，我用GitLab MR + Code Review Checklist，关键模块会本地拉代码跑一遍。反馈时我会先肯定做得好的地方，再指出需要改进的点，并给出具体建议（不只是说'这里不对'，而是说'这里建议改成XXX，因为YYY'）。

目标是让代码质量提升，同时让团队成员感受到尊重和成长。"

## 五、薪资与期望

### 13. 当前薪资情况？

**答题策略**：
- **如实回答**：不要虚报（背调会查）
- **拆分说明**：月薪 + 年终奖 + 其他福利
- **适当留余地**：如果当前偏低，可以解释原因（如"因为是传统行业，薪资结构偏保守"）

**回答示例**：
"我当前月薪是X元，年终奖约X个月，年总包约X万。公司有五险一金和正常的节假日福利。因为是传统行业（地大）/教育行业（讯飞），薪资结构相对保守，我这次求职希望能在薪资和职业发展上都有所提升。"

### 14. 期望薪资？

**答题策略**：
- **做好市场调研**：查Boss直聘、拉勾等平台的同岗位薪资范围
- **给出区间**：不要报死数字，给20%-30%的浮动空间
- **强调价值匹配**：期望薪资是基于能力和市场行情

**回答示例**：
"我了解到AI应用全栈工程师在武汉/北京的市场行情大概是X-Y万/年。结合我的能力（6年前端经验+全栈转型+RAG项目上线），我期望的年总包在X-Y万之间，具体可以根据岗位要求和公司情况协商。我更看重的是这个岗位能否让我在AI Agent方向深入、有技术成长空间，薪资在合理范围内都可以接受。"

### 15. 如果我们只能给X万（低于期望），你怎么办？

**答题策略**：
- **不要立即拒绝**：表示理解
- **权衡其他因素**：技术栈、团队、成长空间
- **给自己留退路**：不要当场答应

**回答示例**：
"我理解每个公司都有自己的薪资体系。薪资虽然重要，但不是我唯一考虑的因素。如果这个岗位在技术栈、团队氛围、成长空间上都很契合，薪资在我能接受的底线以上，我愿意考虑。具体我需要综合评估后再给答复，希望能给我一些时间考虑。"

**答题策略**：
- **诚实回答**：说明在看其他机会（正常求职状态）
- **不透露具体公司**：保护隐私和谈判空间

- **给出时间范围**

**回答示例**：
"我当前项目预计X月底会解散，我需要做好工作交接和离职手续，大概需要2-4周时间。如果贵司这边比较急，我可以和当前公司沟通，尽量在X周内完成交接。具体时间我们可以协商。"

## 使用建议

1. **提前准备**：把这些回答熟悉一遍，不要背诵，理解逻辑
