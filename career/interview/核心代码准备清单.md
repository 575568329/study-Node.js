## 一、RAG核心代码（必须准备）

### 代码1：RAG Pipeline完整流程

**场景**：面试官说"手写一个文档入库的核心流程"

**代码**（JavaScript/TypeScript）：
```javascript
// 文档入库：加载 → 切片 → Embedding → 向量存储
async function ingestDocument(filePath, kbId) {
  try {
    // 1. 加载文档
    const loader = getDocumentLoader(filePath); // 根据扩展名选择loader
    const rawDoc = await loader.load();
    
    // 2. 切片
    const textSplitter = new RecursiveCharacterTextSplitter({
      chunkSize: 500,
      chunkOverlap: 50,
    });
    const chunks = await textSplitter.splitDocuments(rawDoc);
    
    // 3. Embedding
    const embeddings = new OpenAIEmbeddings(); // 或GLM/BGE
    const vectorStore = await VectorStore.fromDocuments(
      chunks,
      embeddings,
      { kbId } // 知识库隔离
    );
    
    // 4. 保存元数据（文件名、路径、所属知识库）
    await saveDocumentMeta({
      filePath,
      kbId,
      chunkCount: chunks.length,
      uploadedAt: new Date(),
    });
    
    return { success: true, chunkCount: chunks.length };
  } catch (error) {
    console.error('Document ingestion failed:', error);
    throw error;
  }
}

// 根据文件扩展名选择loader
function getDocumentLoader(filePath) {
  const ext = path.extname(filePath);
  switch (ext) {
    case '.txt':
    case '.md':
      return new TextLoader(filePath);
    case '.pdf':
      return new PDFLoader(filePath);
    case '.docx':
      return new DocxLoader(filePath);
    default:
      throw new Error(`Unsupported file type: ${ext}`);
  }
}
```

**面试官可能追问**：
- "如果文件很大（100MB），怎么优化？" → Stream处理，分批入库
- "如果Embedding失败怎么办？" → Retry 3次，失败记录到错误队列，人工介入
- "chunkSize和overlap怎么定的？" → 500 token平衡语义完整性和检索精度，overlap 10%避免边界信息丢失

### 代码2：混合检索（向量+关键词+RRF融合）

**场景**：面试官说"手写混合检索的实现，包括RRF算法"

**代码**：
```javascript
// 混合检索：向量相似度 + 关键词匹配 + RRF融合
async function hybridSearch(query, kbId, topK = 5) {
  // 1. 向量检索
  const vectorResults = await vectorStore.similaritySearch(query, {
    filter: { kbId },
    k: topK,
  });
  
  // 2. 关键词检索（BM25）
  const keywordResults = await keywordSearch(query, kbId, topK);
  
  // 3. RRF融合
  const fusedResults = rrfFusion([vectorResults, keywordResults], topK);
  
  return fusedResults;
}

// BM25关键词检索（简化版）
async function keywordSearch(query, kbId, topK) {
  // 实际项目中用Elasticsearch或本地实现BM25
  const allChunks = await getChunksByKbId(kbId);
  const scores = allChunks.map(chunk => ({
    chunk,
    score: bm25Score(query, chunk.text), // BM25算法计算分数
  }));
  
  return scores
    .sort((a, b) => b.score - a.score)
    .slice(0, topK)
    .map(item => item.chunk);
}

// RRF算法：Reciprocal Rank Fusion
function rrfFusion(resultSets, topK, k = 60) {
  const scoreMap = new Map(); // docId -> score
  
  // 遍历每路检索结果
  resultSets.forEach(results => {
    results.forEach((doc, rank) => {
      const docId = doc.id;
      const rrfScore = 1 / (k + rank + 1); // rank从0开始，所以+1
      
      if (scoreMap.has(docId)) {
        scoreMap.set(docId, scoreMap.get(docId) + rrfScore);
      } else {
        scoreMap.set(docId, rrfScore);
      }
    });
  });
  
  // 按融合分数排序
  const sortedDocs = Array.from(scoreMap.entries())
    .sort((a, b) => b[1] - a[1]) // 按score降序
    .slice(0, topK)
    .map(([docId]) => getDocById(docId)); // 根据docId查询完整文档
  
  return sortedDocs;
}
```

**面试官可能追问**：
- "RRF的k=60是怎么来的？" → 论文默认值，经验证对大多数场景有效，可以调参优化
- "如果两路检索结果重复怎么办？" → RRF会自动累加分数，重复出现的doc分数更高（这正是RRF的优势）
- "为什么不直接加权平均？" → RRF不依赖绝对分数，只看排名，更鲁棒

### 代码3：SSE流式响应

**场景**：面试官说"手写Next.js的SSE流式响应接口"

**代码**：
```javascript
// app/api/chat/route.ts
export async function POST(req: Request) {
  const { query, kbId } = await req.json();
  
  // 创建可读流
  const stream = new ReadableStream({
    async start(controller) {
      try {
        // 1. 检索相关文档
        const docs = await hybridSearch(query, kbId, 5);
        
        // 2. 构建Prompt
        const context = docs.map(d => d.text).join('\n\n');
        const prompt = buildPrompt(query, context);
        
        // 3. 调用LLM流式生成
        const llmStream = await llm.stream(prompt);
        
        // 4. 逐token推送
        for await (const chunk of llmStream) {
          const text = chunk.text || '';
          controller.enqueue(new TextEncoder().encode(`data: ${text}\n\n`));
        }
        
        // 5. 推送来源引用
        const sources = docs.map(d => ({ file: d.fileName, page: d.page }));
        controller.enqueue(
          new TextEncoder().encode(`data: ${JSON.stringify({ sources })}\n\n`)
        );
        
        controller.close();
      } catch (error) {
        controller.error(error);
      }
    },
  });
  
  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
    },
  });
}

// 构建Prompt模板
function buildPrompt(query, context) {
  return `你是一个专业的文档问答助手。请基于以下文档片段回答用户问题。

【重要规则】
1. 必须基于提供的文档内容回答，不能编造信息
2. 如果文档中没有相关内容，明确告诉用户"文档中未找到相关信息"

【文档片段】
${context}

【用户问题】
${query}

【回答】`;
}
```

**面试官可能追问**：
- "SSE和WebSocket区别？" → SSE单向（服务端推客户端），WebSocket双向；RAG问答场景SSE够用
- "如果用户中途关闭页面怎么办？" → controller会检测到断开，自动停止流
- "如何处理超时？" → 设置timeout，超过30秒未完成则abort

### 代码4：requestAnimationFrame分批渲染

**场景**：面试官说"你的GIS项目是怎么做分批渲染的？写一下核心代码"

**代码**：
```javascript
// 分批渲染大量监测点，避免主线程阻塞
function renderPointsInBatches(points, map, batchSize = 100) {
  let index = 0;
  
  function renderBatch() {
    // 取当前批次的点
    const batch = points.slice(index, index + batchSize);
    
    // 渲染到地图上
    batch.forEach(point => {
      map.addMarker({
        position: [point.lng, point.lat],
        icon: getIcon(point.status), // 根据状态显示不同图标
        data: point,
      });
    });
    
    // 更新进度
    index += batchSize;
    
    // 如果还有剩余，下一帧继续
    if (index < points.length) {
      requestAnimationFrame(renderBatch);
    } else {
      console.log('All points rendered');
    }
  }
  
  // 启动渲染
  renderBatch();
}

// 根据监测点状态返回图标
function getIcon(status) {
  switch (status) {
    case 'warning':
      return 'icon-warning.png';
    case 'normal':
      return 'icon-normal.png';
    case 'offline':
      return 'icon-offline.png';
    default:
      return 'icon-default.png';
  }
}

// 使用示例
const points = await fetchMonitoringPoints(provinceId); // 假设返回8000个点
renderPointsInBatches(points, map, 100); // 每帧100个
```

**面试官可能追问**：
- "为什么每帧100个？" → 经验值，100个点渲染约10ms，16.6ms帧预算内
- "如果用户缩放地图怎么办？" → 监听zoom事件，重新过滤数据并renderBatches
- "为什么不用Web Worker？" → 地图操作需要DOM，Worker无法访问DOM

### 代码5：虚拟滚动（大列表优化）

**场景**：面试官说"如果监测点列表有10000条，怎么优化？"

**代码**（React示例）：
```javascript
import { useVirtualizer } from '@tanstack/react-virtual';

function MonitoringPointList({ points }) {
  const parentRef = useRef(null);
  
  // 虚拟滚动：只渲染可见区域
  const virtualizer = useVirtualizer({
    count: points.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 60, // 每行高度60px
    overscan: 5, // 上下各多渲染5行，避免滚动时白屏
  });
  
  return (
    <div ref={parentRef} style={{ height: '600px', overflow: 'auto' }}>
      <div style={{ height: virtualizer.getTotalSize() }}>
        {virtualizer.getVirtualItems().map(virtualRow => (
          <div
            key={virtualRow.index}
            style={{
              position: 'absolute',
              top: 0,
              left: 0,
              width: '100%',
              height: `${virtualRow.size}px`,
              transform: `translateY(${virtualRow.start}px)`,
            }}
          >
            <MonitoringPointRow point={points[virtualRow.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

**面试官可能追问**：
- "虚拟滚动的原理？" → 只渲染可见区域+缓冲区的DOM，滚动时动态更新
- "为什么要overscan？" → 快速滚动时，提前渲染上下几行，避免白屏
- "如果每行高度不固定怎么办？" → 用 `measureElement` 动态测量

### 核心设计要点（能讲清楚）

#### 1. 文档上传与入库

**设计决策**：
- **同步 vs 异步**：上传同步返回（秒级），入库异步处理（消息队列）
- **原因**：Embedding耗时（1000 chunks约10秒），同步会超时
- **实现**：上传成功 → 返回taskId → 前端轮询/WebSocket获取进度

**代码示例**：
```javascript
// 上传接口（同步）
POST /api/documents/upload
{
  file: File,
  kbId: string
}
→ { taskId: 'xxx', status: 'pending' }

// 入库任务（异步，消息队列消费）
async function processIngestTask(taskId) {
  try {
    await ingestDocument(filePath, kbId);
    await updateTaskStatus(taskId, 'completed');
  } catch (error) {
    await updateTaskStatus(taskId, 'failed', error.message);
    // 重试3次后放入死信队列，人工介入
  }
}
```

#### 2. 向量存储选型

**本地 vs 云服务**：
| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| **本地JSON FileStore** | 免费、简单、无外部依赖 | 性能差（<1万文档）、无分布式 | MVP、Demo、小规模 |
| **自建Chroma** | 免费、性能好（HNSW）、可控 | 需要运维、扩展需手动 | 中等规模（10万-百万） |
| **云服务Pinecone** | 性能强、免运维、自动扩展 | 成本高（$70/月起）、数据出境 | 大规模（百万+）、有预算 |

**你的项目当前选择**：本地JSON FileStore
**迁移计划**：文档量>1万时迁移Chroma，>10万时考虑Pinecone

#### 3. 成本优化

**问题**：GLM-4-flash API调用成本（embedding + LLM）

**优化方案**：
1. **Embedding缓存**：同一文档重复上传，不重复embedding
2. **检索结果缓存**：热点query（如"如何配置环境变量"）缓存24小时
3. **Chunk去重**：不同文档的重复chunk只embedding一次
4. **降采样**：历史对话只保留最近3轮，不无限堆积上下文

**预估成本**（100用户/天，每人10次问答）：
- Embedding：1000次/天 × $0.0001/次 = $0.1/天
- LLM：1000次/天 × $0.001/次 = $1/天
- 总计：$1.1/天 × 30天 = $33/月

#### 4. 扩展性设计

**如何支持10万+文档？**
1. **向量存储**：迁移Chroma（支持分布式）
2. **检索优化**：分级检索（先粗排Top-50，再精排Top-5）
3. **缓存升级**：Redis集群 + CDN缓存静态资源
4. **负载均衡**：API Gateway后挂多个Node.js实例

**如何支持百万级并发？**
1. **限流**：每用户10 QPS，防止单用户打爆
2. **降级**：API失败时返回缓存结果或"服务繁忙"
3. **熔断**：连续失败5次后熔断30秒
4. **异步化**：所有耗时操作（embedding、LLM调用）走消息队列

### 面试官会问的trade-off

#### Q1："为什么选LangChain而不是LlamaIndex？"
**回答**：
- LangChain灵活、生态好、支持多种模型
- LlamaIndex专注RAG、开箱即用，但定制能力弱
- 我的项目需要LangGraph做Agent工作流，LangChain更合适
- 如果纯做RAG、不需要复杂工作流，LlamaIndex更简单

#### Q2："如何处理文档更新（增量索引）？"
**回答**：
- **删除旧版本**：根据docId删除向量库和元数据
- **重新入库**：新版本走完整入库流程
- **增量更新**：如果只改一小段，只更新对应chunk（需要chunk级别的版本管理）
- **你的项目当前**：全删全插（简单粗暴），后续优化成增量更新

#### Q3："如何做权限隔离（多租户）？"
**回答**：
- **知识库级隔离**：每个用户有自己的kbId，检索时filter by kbId
- **向量库隔离**：不同租户的向量存在不同collection
- **业务数据库隔离**：userId + kbId联合查询，确保用户只能访问自己的数据
- **你的项目当前**：单用户（个人项目），多租户是生产环境需要加的
