# 讯飞澳门项目3分钟讲稿

更新时间：2026-06-11

## 3分钟完整版

这个项目是智学网面向澳门教育市场的出海改造。智学网在内地服务2500+学校，现在要拓展港澳市场，我们这个项目组大约60人，负责把资源加工平台、题库管理、众包加工这几个核心系统做国际化和澳门业务规则适配。

我的角色是前端负责人。原来的前端骨干离职后，我接手了5个遗留系统（资源管理平台rmp、资源加工平台rpp-web、题库管理tkms-fresh-web、众包加工crowdsourced-new-web、专题教材管理gxh-erm）的前端改造工作，从需求落地到上线验收全程负责。这几个系统技术栈是Vue2 + Vuex + Element UI + webpack，还有一个用Angular 4写的题目编辑器模块。

这个项目核心难点有两个：**第一个是i18n双语言决策体系，第二个是富文本公式编辑器的组件化沉淀**。

先说i18n这块。澳门项目不是简单的界面翻译，而是"工作室语言（资源加工区）"和"页面语言（导航菜单）"必须同时存在。举个例子，用户在简体中文界面下，可能在编辑繁体中文的澳门试题，这时候导航菜单显示简体，但编辑器右侧的知识点、题型下拉必须显示繁体。我设计了一个resolveBizLocale()函数，按路由级判断当前页面属于资源加工区还是系统管理区，资源加工区跟工作室语言，其他区域跟用户偏好语言。

语言文件这块，原来是一个巨型JSON，多人协作经常冲突。我把它按8个业务模块拆成32个JSON（简/繁/英/葡4种语言 × 8个模块），用webpack的require.context自动加载，这样每个人改自己负责的模块文件，提交时不会互相覆盖。

为了防止漏翻和路径错位，我设计了一个i18n-check卡口脚本，接入husky pre-commit。这个脚本用的是基线增量策略：首次跑通后把当前所有问题记录为基线，后续提交时只拦截新增问题，不拦截存量。这样既不阻塞历史遗留问题，又能保证新代码不引入新的翻译漏洞。当前基线已经从最初的几百条问题修复至0。这个脚本是用Claude Code辅助实现的，我负责设计拦截规则和基线策略，AI生成初版代码，我做code review和逻辑调整。

第二个难点是富文本公式编辑器的组件化。系统里有多个编辑器场景——题目编辑、解析编辑、标注审核、相似题对比，每个场景都要处理公式渲染，但原来的代码都是分散复制粘贴。我把Wiris图片公式、LaTeX、MathJax、图片兜底这四条渲染链路抽象成三层组件：原子组件（单个公式渲染器）、通用组件（带工具栏的编辑器）、业务组件（接入具体业务场景的封装）。这样新场景只需要引入对应层级的组件，不用再复制一遍渲染逻辑。

在实施过程中，我识别出一个系统级风险：这几个子项目之间存在互相依赖，比如rmp依赖rpp-web的某个工具函数，但它们用的Element UI版本不一致。我制定了隔离方案，把共享代码抽到独立npm包，同时在组件设计时做好版本兼容标注，避免升级一个系统导致其他系统崩溃。

整个项目我完成了270+次非合并提交和900+文件变更。我借助AI工具（Claude Code和Cursor）提升需求拆解和重复性改造效率，但方案判断、架构决策、代码审查和业务验证都由我把关。AI主要用在代码生成、重复性改造（比如给每个页面加语言切换逻辑）和回归检查，我会明确告诉AI要改什么、不能动什么，生成的代码我都会逐行review，确保符合项目规范和业务语义。

项目最终在不影响大陆原流程的前提下完成澳门4语言（简/繁/英/葡）交付，支撑了澳门市场上线。
