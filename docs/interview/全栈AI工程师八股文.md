## 一、AI 应用链路（核心竞争力）

### 1. RAG（检索增强生成）

**Q1: 什么是 RAG？为什么需要 RAG？**
- **概念**：Retrieval-Augmented Generation，检索增强生成。将外部知识库与大模型结合，先检索相关文档，再将检索结果作为上下文让模型生成回答。
- **Why RAG**：
  - 解决大模型知识截止日期问题（训练数据过时）
  - 解决幻觉问题（模型编造不存在的信息）
  - 支持私域知识（企业内部文档、专业领域知识）
  - 降低成本（无需重新训练模型）

**Q2: RAG 的核心流程是什么？**
```
文档上传 → 文本切片 → 向量化 → 存储 → 检索 → 生成回答 → 来源引用
```
- **文本切片**：按标题分段 + 固定窗口（如 512 tokens），保持语义完整
- **向量化**：将文本转为向量（Embedding），批量生成提升效率
- **混合检索**：向量相似度 + 关键词匹配，提升召回准确率
- **来源引用**：透出文件名、章节、相关性分数，增强可信度

**Q3: 如何解决 RAG 召回不准和幻觉问题？**
- **召回阶段**：
  - 设置相似度阈值（如 0.7），过滤低质量片段
  - 使用混合检索（向量 + BM25 关键词）
  - 优化切片策略（保持语义完整性）
- **生成阶段**：
  - 显式区分"知识库引用"与"AI 补充"
  - 透出 Top-K 来源和分数供用户验证
  - Prompt 中明确要求"不知道就说不知道"

**Q4: 你项目中的 RAG 实现有什么特点？**
- **双重标注**：当知识库无相关内容时明确标注为"AI 补充回答"，降低混淆风险
- **来源透出**：展示文件名、章节、相关性分数，用户可验证
- **抽象化设计**：封装可复用 RAG Pipeline，支持 FileStore / ChromaDB 切换

### 2. LangChain 与 LangGraph

**Q5: LangChain 是什么？解决什么问题？**
- **定位**：LLM 应用开发框架，提供标准化的组件和链路
- **核心能力**：
  - **链（Chains）**：串联多个步骤（如检索 → 生成 → 格式化）
  - **代理（Agents）**：让模型自主决策调用工具
  - **记忆（Memory）**：管理对话上下文
  - **工具（Tools）**：外部能力接入（搜索、计算器、数据库）

**Q6: LangGraph 相比 LangChain 有什么优势？**
- **LangChain**：线性链路，适合固定流程
- **LangGraph**：
  - 支持**条件分支**（if-else 逻辑）
  - 支持**循环**（agent 工具调用可能失败重试）
  - **状态管理**：显式定义状态流转
  - **可视化**：生成流程图，便于调试

**Q7: 你项目中如何使用 LangGraph？**
- 构建支持条件分支、工具调用和状态管理的 AI Agent 工作流
- 示例流程：
  ```
  [用户提问] → [判断：需要检索吗？]
       ├─ 是 → [检索知识库] → [生成回答]
       └─ 否 → [直接生成回答]
  ```

### 3. SSE 流式响应

**Q8: 为什么 AI 应用需要流式响应？如何实现？**
- **Why**：大模型生成需要时间，流式输出提升用户体验（类似 ChatGPT 逐字显示）
- **技术选型**：SSE（Server-Sent Events）vs WebSocket
  - **SSE**：单向推送，HTTP 协议，轻量简单
  - **WebSocket**：双向通信，适合实时协作
  - AI 问答场景：SSE 足够（服务端推送 tokens，客户端渲染）

**Q9: SSE 实现的关键点？**
```javascript
// 后端（Node.js）
res.setHeader('Content-Type', 'text/event-stream');
res.setHeader('Cache-Control', 'no-cache');
res.setHeader('Connection', 'keep-alive');

for await (const chunk of stream) {
  res.write(`data: ${JSON.stringify(chunk)}\n\n`);
}
res.end();

// 前端
const eventSource = new EventSource('/api/chat');
eventSource.onmessage = (event) => {
  const chunk = JSON.parse(event.data);
  // 逐步渲染
};
```

### 4. 知识图谱

**Q10: 知识图谱在 RAG 中的作用？**
- **传统 RAG**：向量检索，语义相似但缺乏结构化关系
- **知识图谱增强**：
  - 实体识别（人名、地名、概念）
  - 关系抽取（A 是 B 的子类、X 影响 Y）
  - 图谱搜索（多跳推理：A → B → C）

**Q11: 你项目中的知识图谱实现？**
- 文档上传后异步抽取实体和关系
- 生成三类节点：文档节点、实体节点、关系边
- 基于 Graphology 库实现图谱搜索、节点详情和收藏
- 与 RAG 打通：kbId 保持知识库选择、对话上下文和图谱视图同步

## 二、前端与全栈

### 5. Vue2 vs Vue3

**Q12: Vue2 和 Vue3 的核心差异？**
| 维度 | Vue2 | Vue3 |
|------|------|------|
| 响应式 | Object.defineProperty | Proxy |
| API 风格 | Options API | Composition API |
| 性能 | 组件更新粒度较粗 | 编译优化 + Tree-shaking |
| TypeScript | 支持较弱 | 原生 TS 支持 |
| 生命周期 | beforeCreate/created/... | setup() + onMounted/... |

**Q13: 为什么 Vue3 使用 Proxy 而不是 Object.defineProperty？**
- **Vue2 限制**：
  - 无法检测数组索引和长度变化
  - 无法检测对象属性的新增/删除
  - 需要 Vue.set / Vue.delete 补丁
- **Proxy 优势**：
  - 拦截整个对象，支持数组和动态属性
  - 性能更好（懒代理，按需触发）

### 6. React 与 Next.js

**Q14: React 的核心思想？**
- **声明式 UI**：描述"是什么"而非"怎么做"
- **组件化**：UI 拆分为可复用单元
- **单向数据流**：props 从父到子，事件从子到父
- **虚拟 DOM**：diff 算法减少真实 DOM 操作

**Q15: Next.js 相比 Create React App 有什么优势？**
- **SSR/SSG**：服务端渲染 / 静态生成，SEO 友好
- **文件路由**：pages 目录自动生成路由
- **API Routes**：内置后端接口支持
- **App Router（13+）**：React Server Components，流式渲染
- **性能优化**：自动代码分割、图片优化、字体优化

**Q16: 你项目中 Next.js 的应用？**
- 基于 App Router 构建数据/对话/图谱三工作区
- 通过 kbId 参数保持知识库选择、文档状态、对话上下文和图谱视图同步
- SSE 流式问答与 React 状态管理结合

### 7. i18n 国际化

**Q17: 前端国际化的核心难点？**
- **语言切换**：用户偏好 vs 页面语言 vs 业务数据语言
- **文本管理**：大量翻译文件的组织和维护
- **动态内容**：后端返回的多语言数据
- **格式差异**：日期、货币、数字格式

**Q18: 你项目中的双语言决策架构？**
- **核心难点**："工作室语言（资源加工区）"与"页面语言（导航/菜单）"同页面共存
- **解决方案**：
  - 统一收口至 `resolveBizLocale()` 按路由级判断
  - 请求层注入语言上下文请求头，前后端一致
  - vue-i18n 文件按 8 个业务模块拆分为 32 个 JSON（4 语言 × 8 模块）
  - webpack `require.context` 自动加载，多人零冲突协作

**Q19: 自研 i18n-check 卡口脚本的设计？**
- **问题**：人工检查 4 语言易漏翻、路径错位
- **方案**：
  - 借助 AI 工具（Claude Code / Codex）实现
  - 接入 husky pre-commit 钩子
  - 基线增量策略：只拦截新增/修改的 key
  - 拦截两类问题：「路径错位 key」与「漏翻」
  - 存量基线修复至 0

## 三、性能优化

### 8. 前端性能优化

**Q20: 你如何优化地灾驾驶舱的性能？**
- **问题**：十万级监测数据展示 + 三维地图渲染拥堵 + 首屏加载卡顿
- **方案**：
  - **分级加载**：先加载可视区域数据，滚动/缩放时按需加载
  - **显示时序控制**：图表 → 二维地图 → 三维模型，逐步渲染
  - **数据聚合**：缩小级别时聚合显示（如 100 个点合并为 1 个集群）
  - **防抖节流**：地图移动/缩放事件防抖
- **效果**：首页加载提升约 50%，首屏从 3.5s → 1.8s

**Q21: 前端性能优化的通用手段？**
- **加载优化**：代码分割、懒加载、预加载、CDN
- **渲染优化**：虚拟滚动、防抖节流、Web Worker
- **网络优化**：HTTP/2、Gzip、缓存策略、接口合并
- **打包优化**：Tree-shaking、Scope Hoisting、图片压缩

## 四、工程化

### 9. Webpack vs Vite

**Q22: Vite 相比 Webpack 有什么优势？**
| 维度 | Webpack | Vite |
|------|---------|------|
| 启动速度 | 慢（全量打包） | 快（ESM 按需加载） |
| 热更新 | 相对慢 | 极快（精准更新） |
| 生产构建 | 成熟稳定 | 基于 Rollup |
| 生态 | 丰富 | 快速增长 |
| 适用场景 | 大型复杂项目 | 现代前端项目 |

**Q23: Webpack 的核心概念？**
- **Entry**：入口文件
- **Output**：输出目录和文件名
- **Loader**：转换非 JS 文件（如 .vue、.scss）
- **Plugin**：扩展功能（如压缩、提取 CSS）
- **Code Splitting**：代码分割策略

### 10. Git 与协作

**Q24: Git rebase 和 merge 的区别？**
- **merge**：保留分支历史，生成合并提交
- **rebase**：将当前分支的提交"挪到"目标分支最新提交之后，历史线性
- **选择**：
  - 团队协作：merge（历史清晰）
  - 个人分支：rebase（保持主线整洁）
  - **黄金法则**：不要 rebase 已推送到公共分支的提交

**Q25: 如何设计 Git 提交规范？**
- **Conventional Commits** 格式：
  ```
  <type>(<scope>): <subject>

  <body>

  <footer>
  ```
- **type**：feat / fix / refactor / docs / chore / test
- **工具**：commitlint + husky 强制规范
- **好处**：自动生成 CHANGELOG、语义化版本

## 五、项目经验追问

### 11. i18n 改造项目

**Q26: 为什么选择 vue-i18n 而不是自己实现？**
- **生态成熟**：Vue 官方推荐，文档完善
- **功能完整**：复数、日期格式化、插值、懒加载
- **性能优化**：缓存、按需加载
- **自己实现**：成本高，易出 bug，维护难

**Q27: 如何保证 4 语言翻译质量？**
- **技术卡口**：i18n-check 脚本拦截漏翻和路径错位
- **流程卡口**：翻译人员提供翻译文件 → 前端录入 → 自动化检查 → code review
- **业务验收**：澳门方业务人员验收葡语和繁体

---

### 12. 富文本编辑器

**Q28: 富文本公式编辑器的技术难点？**
- **多格式共存**：Wiris 图片公式 + LaTeX + MathJax + 图片兜底
- **渲染链路**：优先 Wiris → 降级 LaTeX → 降级 MathJax → 兜底图片
- **组件化**：多系统复用（Angular 4 + Vue2 项目）
- **版本兼容**：不同子项目依赖不同版本的 MathJax

**Q29: 如何设计组件三层抽象？**
- **原子组件**：单一渲染逻辑（如 `MathJaxRenderer`）
- **通用组件**：组合原子组件 + 降级策略（如 `FormulaRenderer`）
- **业务组件**：通用组件 + 业务逻辑（如 `QuestionEditor`）

### 13. GIS 可视化

**Q30: OpenLayers 和 Leaflet 的区别？**
- **Leaflet**：轻量、简单、移动端友好，适合简单地图
- **OpenLayers**：功能强大、支持多种坐标系和投影、适合复杂 GIS
- **选择**：地质灾害项目需要国家 2000 坐标系 + 三维模型 → OpenLayers
