# 组件库设计方案

更新时间：2026-05-07

## 目标

建立一个小而准的 React + TypeScript 组件库，用来证明：

1. 具备组件分层设计能力。
2. 能设计清晰的组件 API。
3. 能把真实业务项目经验沉淀成可复用组件。
4. 能支撑 RAG 工作台、AI 应用后台和业务管理系统。

这个组件库不是为了替代 Ant Design，而是为了面试时能讲清楚自己的组件设计方法。

## 项目定位

建议名称：

```text
fullstack-ui-kit
```

定位：

**面向 AI 应用后台 / RAG 工作台 / 业务管理系统的 React + TypeScript 组件库。**

核心场景：

- 文档上传。
- RAG 来源引用。
- AI 对话消息。
- Agent / LangGraph 执行步骤展示。
- 管理系统表格、弹窗、提示。

## 项目路径

建议放在当前仓库：

```text

```

原因：

## 组件分层

### 1. 基础组件

只关心 UI 和基础交互，不绑定业务。

- Button
- Input
- Modal
- Toast
- Tabs

要求：

- Props 类型清楚。
- 支持基础状态：disabled、loading、error 等。
- 样式可复用。

### 2. 通用业务组件

带有常见后台业务状态，但不绑定具体业务领域。

- DataTable
- UploadPanel

要求：

- 支持 loading / empty / error。
- 支持事件回调。
- 支持受控数据输入。

### 3. AI / RAG 场景组件

服务 AI 应用和 RAG 工作台。

- SourceCard
- ChatMessage
- StepTimeline

要求：

- 能展示 RAG 来源引用。
- 能展示 AI 对话内容。
- 能展示 Agent 执行步骤。
- 能直接支撑面试讲解。

## 组件 API 设计原则

1. Props 用 interface 定义并导出。
2. 组件保持受控优先，必要时支持 defaultValue。
3. 事件回调用 `onXxx` 命名。
4. loading / error / empty 状态显式建模。
5. 业务组件不直接请求接口，数据由外部传入。
6. 样式不依赖全局污染。
7. 不为了抽象而抽象，真实复用两次以上再上复杂配置。

## 和 RAG 主项目的关系

组件库不是独立炫技项目，必须服务 RAG 主项目：

- `UploadPanel` 对应文档上传。
- `SourceCard` 对应来源引用。
- `ChatMessage` 对应 AI 问答。
- `StepTimeline` 对应 Agent / LangGraph 执行过程。

后续可以选择：

1. 从 RAG 项目抽组件到组件库。
2. 先在组件库实现，再接回 RAG 项目。
3. 保持组件库作为独立证明项目，不强制接入。

优先建议：先独立实现，再挑 1-2 个组件接回 RAG 项目。
