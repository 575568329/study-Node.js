# Codex with CC 子代理工作流

更新时间：2026-05-07

## 目标

把 Codex 的主线程能力和子代理能力结合起来，形成一套可重复、可验证、可回收的协作流程。

这个工作流的核心不是“多开代理”，而是：

- 主线程负责判断方向和控制边界。
- 子代理负责在明确作用域里并行推进。
- 最后由主线程统一整合和验收。

## 适用场景

适合使用子代理的任务：

1. 任务涉及 3 个以上文件域或模块。
2. 需要同时做调查、实现、验证或审查。
3. 需要把大任务拆成多个互不冲突的子任务。
4. 需要降低单线程上下文污染，避免边做边忘。

不适合使用子代理的任务：

1. 单文件小改动。
2. 只读定位问题。
3. 需求还没明确。
4. 任务太小，拆分成本高于收益。

## 核心分工

### 主线程

职责：

- 明确目标。
- 拆分任务。
- 分配文件范围。
- 控制依赖顺序。
- 汇总结果。
- 决定是否继续派生下一轮子任务。

主线程不做的事：

- 不把所有细节都自己重做一遍。
- 不让子代理互相覆盖改动。
- 不把未验证的子代理结论当最终结论。

### 实现子代理

职责：

- 只负责被分配的文件或模块。
- 独立完成实现。
- 保持和其他子代理的边界清晰。

输出：

- 修改文件列表。
- 完成内容摘要。
- 验证方式。
- 风险说明。

### 调查子代理

职责：

- 做源码定位。
- 梳理调用链。
- 找边界条件和触发条件。
- 输出可 grep 的关键字符串、类名、方法名和路径。

适合任务：

- “哪个路由打开了这个页面？”
- “这个报错什么情况下会出现？”
- “数据从哪传到哪？”

### 审查子代理

职责：

- 找 bug。
- 找回归。
- 找遗漏测试。
- 找边界缺口。

审查重点：

- 交互是否闭环。
- 状态是否一致。
- 是否有隐藏副作用。
- 是否破坏既有行为。

## 调度原则

1. 先拆任务，再派代理。
2. 每个子代理只拿一块明确作用域。
3. 作用域之间尽量互斥。
4. 关键链路至少有一个审查子代理复核。
5. 最终合并由主线程负责。

## 推荐流程

### 1. 规划

主线程先输出：

- 任务目标。
- 子任务列表。
- 每个子任务的文件范围。
- 依赖顺序。
- 验收标准。

### 2. 派发

把子任务拆成以下类型：

- 实现型。
- 调查型。
- 审查型。

### 3. 并行执行

子代理并行推进，但不能互相改同一组文件。

### 4. 汇总

主线程收集结果，检查：

- 文件是否冲突。
- 验证是否真实执行。
- 风险是否说明清楚。
- 是否需要第二轮代理。

### 5. 收口

主线程统一整理最终方案、更新文档和 memory。

## 输出模板

子代理返回建议至少包含：

```text
1. 负责范围
2. 修改文件
3. 完成内容
4. 验证方式
5. 风险与未完成项
6. 和其他子任务的关系
```

## 在当前项目中的落地

这个工作流优先用于：

- RAG 主项目体检和补强。
- `fullstack-ui-kit` 组件库扩展。
- 简历内容整理和面试资产沉淀。
- 大范围代码审查和链路分析。

## 约束

- 不把子代理当成自动补全机器。
- 不在 scope 不清楚时直接并行。
- 不让子代理修改互相依赖的核心文件。
- 主线程必须最终负责结果真实性。
