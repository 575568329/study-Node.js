## 问题1：一个 RAG 项目从用户上传文档到最后模型返回答案，中间完整链路有哪些步骤？

### 你的常见误区

- 只会讲“上传入库链路”，漏掉“检索问答链路”。
- 更像在描述文件处理流程，没有把 RAG 闭环拆成两段。

### 纠偏后正确表述

完整 RAG 闭环应该拆成两段：

1. 入库链路  
   文件上传 -> 文本解析 -> 分块 -> 向量化 -> 写入向量库 -> 保存文件和知识库元数据

2. 问答链路  
   用户提问 -> 确定检索范围 -> 检索相关片段 -> 组装 Prompt -> 调用大模型生成回答 -> 返回答案和来源引用

### 复习要点

- 以后讲 RAG 项目时，始终按“入库链路 + 问答链路”两段讲。
- 这样既有结构，也方便面试官追问。

## 问题2：为什么不能只保存原始文件，而一定要做“分块 + 向量化”？

### 你的常见误区

- 只说“向量数据库更好”，但没把问题说具体。

### 纠偏后正确表述

如果只保存原始文件，不做分块和向量化，每次提问时就很难快速定位和问题最相关的内容，通常只能把整份文档甚至多份文档直接交给模型。这样会带来三个问题：

1. `token` 消耗很大，成本高、响应慢。
2. 无关内容太多，模型容易被噪音干扰，回答偏题。
3. 长文档可能超出上下文窗口，根本无法稳定处理。

做了 `chunk` 和 `embedding` 之后，系统可以先把用户问题映射成检索条件，只召回最相关的几个片段，再把这些片段作为上下文交给大模型生成答案。核心价值是：先筛选，再回答。

### 复习要点

- 记住关键词：`省 token`、`降噪音`、`提高召回准确性`、`避免上下文窗口超限`。

## 问题3：用户提问后，系统从“收到问题”到“返回答案”会经过哪些步骤？

### 你的常见误区

- 容易直接说“把问题向量化，然后查向量库”，但漏掉“先确定检索范围”。
- 容易把“全部模式”说成“系统会自动判断查哪个知识库”，但当前实现并不是这样。

### 纠偏后正确表述

当前项目的问答链路是：

1. 接口收到用户问题和当前 `kbId`。
2. 系统先构造 `searchQuery`，会把最近的对话上下文一起拼进去，优化多轮追问检索。
3. 根据 `kbId` 确定检索范围：
   - 用户已选择某个知识库：只查该知识库。
   - 用户选择“全部”：跨所有知识库统一检索。
4. 将 `searchQuery` 向量化。
5. 到目标知识库集合中做检索，当前 FileStore 模式支持“向量检索 + 关键词检索 + RRF 融合排序”。
6. 取 `topK` 个最相关片段，组装成上下文。
7. 把“用户问题 + 召回片段 + 约束提示”一起交给 LLM 生成答案。
8. 返回答案，同时返回 `sources`，方便前端展示引用来源。

### 复习要点

- 记住：当前“全部”不是 AI 路由，而是跨库统一检索。
- 真实代码位置在 `rag-docs-assistant/src/app/api/chat/route.ts`。

## 问题4：当前项目里，用户选择“全部”时，会不会先判断该查哪个知识库？

### 你的常见误区

- 容易把“后续规划”说成“当前能力”。

### 纠偏后正确表述

不会。当前实现里，选择“全部”时不会先判断“该查哪个库”，而是直接把所有知识库作为一个逻辑检索域，统一做检索并取全局 `topK`。

也就是说：

- 选择单个知识库：显式路由，直接限定范围。
- 选择“全部”：跨所有知识库统一检索。

### 复习要点

- “全部模式 AI 路由”是升级项，不是已完成能力。
- README 已明确写了这一点。

## 问题5：为什么说当前系统其实已经有“规则路由”？

### 你的常见误区

- 以前容易说“规则路由没有办法做”。

### 纠偏后正确表述

当前系统已经有一层显式规则路由：

- 用户选择哪个知识库，就只检索哪个知识库。

这本质上就是规则路由，而且是最强、最稳定的规则。

后续要补的是另一层能力：

- 当用户选择“全部”时，系统代替用户做判断，也就是 AI 路由。

### 复习要点

- 以后不要说“当前没有规则路由”。
- 要说“当前已有显式路由，后续计划补全部模式下的 AI 路由”。

## 问题6：如果以后做“全部模式”的自动知识库选择，应该优先规则路由还是 AI 路由？

### 你的常见误区

- 容易把规则路由说死，说成“没法做”。
- 容易太快跳到 LangGraph。

### 纠偏后正确表述

当前项目阶段更适合优先做 AI 路由，但不是因为规则路由完全不可做，而是因为：

1. 知识库主题和简介更偏自然语言。
2. 用户问题表达自由，不一定命中固定关键词。
3. 一个问题可能和多个知识库同时相关。

所以可以把“知识库名称 + 简介 + 用户问题”交给 LLM，让模型输出候选知识库和置信度。

但实现第一版时，不一定要先上 LangGraph。最小版本使用一次普通 LLM 调用，让它返回结构化 JSON 就够了。只有当后续需要多步决策、回退逻辑、状态追踪时，再考虑 LangGraph。

### 复习要点

- 面试里不要说“规则路由不行”。
- 更稳的说法是：规则路由适合边界稳定的场景，当前项目更适合优先尝试 AI 路由。

## 问题7：AI 路由的输出应该是“只返回一个知识库”，还是“返回多个候选知识库 + 置信度”？

### 你的常见误区

- 容易只想到“让 LLM 选一个最像的库”。

### 纠偏后正确表述

更合理的输出是：

- 返回多个候选知识库 + 对应置信度。

原因：

1. 如果只返回一个知识库，路由一旦选错，后面整条检索链都偏。
2. 返回多个候选库可以先收缩范围，再让后续检索排序决定最终片段。
3. 置信度可以决定是否降级：
   - 高置信：只查前 1 到 2 个候选库。
   - 中置信：查前几个候选库。
   - 低置信：退回全库统一检索。

### 复习要点

- “候选列表 + 置信度 + fallback” 是更像工程方案的表达。

## 问题8：如果改当前项目，AI 路由应该插在 `/api/chat` 的哪个位置？

### 你的常见误区

- 只说“在第 4 步之前”，但没完全说清为什么。

### 纠偏后正确表述

AI 路由的职责是“确定检索范围”，所以应该加在当前 `/api/chat` 的 `resolveKnowledgeBaseScope(kbId)` 之前。

更理想的顺序是：

1. 收到用户问题
2. 构造 `searchQuery`
3. 判断当前是不是“全部模式”
4. 如果是“全部模式”，先执行 AI 路由，得到候选知识库
5. 再根据路由结果缩小检索范围
6. 再做 query embedding 和检索
7. 最后生成回答

### 复习要点

- 先定范围，再检索。
- 这是职责划分更清楚的做法。

## 问题9：当前项目根据文件类型采用什么解析方式，把文件解析成文本？

### 你的常见误区

- 以前只能说“Word 用插件、PDF 用插件、Excel 用插件”，不清楚真实实现。

### 纠偏后正确表述

当前项目使用统一文档解析模块 `src/lib/doc-parser.ts`，按扩展名把不同文件解析成纯文本：

1. `.txt` / `.md`
   直接用 `file.text()` 读取原始文本。

2. `.pdf`
   使用 `pdfjs-dist` 的 `getDocument(...)` 打开 PDF，逐页调用 `getPage(i)` 和 `page.getTextContent()`，把每页里的文本项拼起来，再汇总成完整文本。

3. `.docx`
   使用 `mammoth.extractRawText(...)` 提取 Word 文档纯文本，不保留复杂样式。

4. `.xlsx`
   使用 `ExcelJS` 读取工作簿，逐个工作表遍历前 100 行，把每行单元格内容拼成结构化文本，例如 `A | B | C`，并加上工作表标题。

### 复习要点

- 以后不要再说“用某个插件”这种泛化表述。
- 要能说出具体库名：`pdfjs-dist`、`mammoth`、`ExcelJS`。

## 问题10：你当前对这个项目的整体表述，哪些点最容易说错？

### 容易说错的点

1. 把“演进方案”说成“当前实现”
   - 例如把 SQL、AI 路由、生产级能力说成已经落地。

2. 把“全部模式统一检索”说成“已经会自动选知识库”

3. 把“文档解析方式”说成笼统的插件调用

4. 把“问答模型”说错

   - 当前主要是本地 JSON，不是已经落到 SQL

### 复习要点

- 面试里最重要的不是说得多，而是“现状、规划、限制”边界清楚。

## 一分钟版口述模板

这个项目是一个基于 Next.js 的 AI 知识库检索系统，核心能力包括知识库管理、文档上传解析、向量检索、流式问答和来源追溯。上传链路上，用户先创建知识库，再上传文档，后端会按文件类型解析文本，做切片和 embedding，把文本片段、向量和元数据写入向量库，同时保存文件和知识库的业务数据。问答链路上，如果用户选择单个知识库，就只在该库内检索；如果选择全部，当前实现是跨所有知识库统一检索，再把召回片段和用户问题一起交给大模型生成答案，并返回 sources 供前端展示来源。后续计划是在全部模式下增加 AI 路由，让模型先根据知识库名称、简介和用户问题输出候选知识库及置信度，再缩小检索范围，提高召回精度和响应效率。
