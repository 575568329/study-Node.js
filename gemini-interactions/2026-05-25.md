> 考点一：JWT（JSON Web Token）认证机制
> 1. 底层机制与核心原理
> 
> 在面试中，仅仅回答“JWT 是无状态的、由三部分组成”是不够的。面试官更看重你对密码学签名和状态转移的理解。
> 
> JWT 的核心是基于哈希/非对称加密的防篡改客户端状态存储。
> 
> JWT 结构： [Header].[Payload].[Signature]
> 
> 
> Header（头部）：声明类型（typ: "JWT"）和签名算法（如 HS256、RS256）。Base64URL 编码。
> 
> Payload（负载）：存储声明数据（Claims），如用户 ID（sub）、过期时间（exp）、角色等。注意：它是明文编码的，不是加密的。
> 
> Signature（签名）：核心防篡改防线。服务器将前两部分用密钥（Secret/Private Key）结合 Header 中声明的算法进行加盐哈希或私钥签名。
> 
> Signature=HMACSHA256(Base64URL(Header)+"."+Base64URL(Payload),secret)
> 
> 底层校验流程：
> 当客户端携带 JWT 再次请求时，服务器执行无状态验证。它不需要查询 Redis 或数据库，而是直接把拿到的 Header 和 Payload 用内存中的密钥再计算一次签名。如果计算出的新签名与客户端传来的 Signature 强一致，且 Payload.exp 未过期，则无条件信任该 Token 中的数据。
> 
> 2. 面试常见追问方向
> 
> 追问 1：JWT 如果泄露了怎么办？如何实现强制登出或拉黑某个 Token？
> 
> 深度回答：JWT 核心是无状态，一旦签发在有效期内就绝对有效。要实现强制登出，必须引入轻量级状态。常见方案是 Blacklist（黑名单）机制：将退出的 Token 写入 Redis，并设置过期时间等于 Token 剩余有效时间。每次请求时校验 Redis，虽有状态但只读，性能依然优于传统 Session。
> 
> 追问 2：Access Token（短效）和 Refresh Token（长效）的设计目的是什么？它是如何降低风险的？
> 
> 深度回答：Access Token 通常有效期 15 分钟，降低泄露后的窗口风险。Refresh Token 有效期长（如 7 天），存在数据库或安全持久化层。当 Access Token 过期，前端隐式调用刷新接口，换取新 Token。这样既保证了无状态的高并发能力，又拥有了每 15 分钟一次的“吊销审查权”（刷新时查库）。
> 
> 追问 3：JWT 应该存放在 localStorage 还是 Cookie 中？各有什么安全风险？
> 
> 深度回答：存 localStorage 易受 XSS（跨站脚本攻击） 窃取（脚本可以直接读取 localStorage）；存 Cookie 并设置 HttpOnly; Secure; SameSite=Strict 可以完美防御 XSS，但需要防范 CSRF（跨站请求伪造） 攻击。一般推荐使用配置严格的 HttpOnly Cookie。
> 
> 3. 常见误区
> 
> 误区 1：把敏感信息（如密码、手机号）放进 Payload。
> 
> 纠正：Payload 只是 Base64 编码，任何人都可以通过 jwt.io 瞬间解码。它是防篡改，但不防偷看的。
> 
> 误区 2：盲目追求“绝对无状态”而拒绝配合 Redis。
> 
> 纠正：没有绝对的无状态。在复杂的企业级架构中，权限变更、账号冻结、多端登录挤下线等业务场景，必须配合 Redis 的黑名单或白名单机制，不要为了无状态而牺牲安全可控性。
> 
> 考点二：Node.js 事件循环（Event Loop）中的 setImmediate
> 1. 底层机制与核心原理
> 
> 在 Node.js 中，事件循环是由底层的 libuv 库实现的。
> setImmediate 的底层机制是：它属于事件循环（Event Loop）六个核心阶段中的 check（检查）阶段。
> 
> Node.js 每一轮事件循环的核心阶段简化如下：
> 
> timers：执行 setTimeout 和 setInterval 的回调。
> 
> poll（轮询）：检索新的 I/O 事件；执行 I/O 回调（几乎所有异步回调都在这里）。
> 
> check：执行 setImmediate 的回调。
> 
> 关键的微任务队列（Microtask Queue）：
> process.nextTick 和 Promise.then 不属于 libuv 的任何一个具体阶段。它们属于 V8 引擎维护的微任务队列。在事件循环的每个具体阶段切换（或者在旧版本中是每个回调执行完）的缝隙，Node.js 都会清空微任务队列。
> 
> 2. 面试常见追问方向
> 
> 追问 1：如果在全局作用域（Main Script）同时写一个 setTimeout(fn, 0) 和 setImmediate(fn)，谁先执行？为什么？
> 
> 深度回答：执行顺序是不确定的（取决于机器性能和时钟精度）。 因为进入 timers 阶段时，如果系统的时钟计算（Timer 准备工作）耗时超过了 1ms，setTimeout 就会先执行；如果没有超过 1ms，事件循环会向前推进，穿过 poll 阶段，最终在 check 阶段先执行 setImmediate。
> 
> 追问 2：如果把上述代码放进一个 I/O 回调（比如 fs.readFile）里，谁先执行？
> 
> 深度回答：setImmediate 必然绝对先执行。 因为 I/O 回调是在 poll 阶段执行的。poll 阶段结束后，事件循环的下一个阶段紧接着就是 check 阶段（setImmediate 所在地），而 timers 阶段在下一轮循环。因此顺序是确定且必定的。
> 
> 追问 3：process.nextTick 和 setImmediate 有什么本质区别？高并发下盲目使用 process.nextTick 会有什么后果？
> 
> 深度回答：nextTick 是微任务（在当前阶段立即插队），setImmediate 是宏任务（在下个阶段排队）。如果在一个无限循环或高并发请求中递归调用 process.nextTick，会导致 V8 的微任务队列永远无法清空，事件循环彻底卡死在当前缝隙，引发 I/O 饥饿（I/O Starvation），程序失去响应。
> 
> 3. 常见误区
> 
> 误区 1：直觉上认为 setImmediate（立即）应该比 setTimeout(fn, 0) 执行得更快。
> 
> 纠正：名字和实际行为相反。setTimeout(fn, 0) 在 timers 阶段（循环开头），setImmediate 在 check 阶段（循环靠后）。在 I/O 回调外，后者的执行时机完全受制于系统 1ms 的时间精度差。
> 
> 误区 2：把宏任务队列和微任务队列混为一谈。
> 
> 纠正：必须明确，setTimeout 和 setImmediate 产生的是宏任务（进入 libuv 的阶段队列）；而 Promise 和 process.nextTick 产生的是微任务（由 V8 优先清空）。微任务的优先级高出宏任务一个维度。

## [16:57] 模式：通用 (API)

**问题**: 请简述 React useEffect 闭包陷阱的原因和解决方案，不超过200字。

**Gemini 回复**:
> React 中的 `useEffect` 闭包陷阱通常发生在**依赖项数组（deps）为空或不完整**时。
> 
> ### 原因
> `useEffect` 在组件渲染时捕获了当时的标准闭包。如果依赖项未正确声明（如设为 `[]`），副作用函数**只会执行一次**。当内部异步操作或定时器触发时，它们引用的仍是**首次渲染时的旧状态（Stale State）**，无法获取最新值。
> 
> ### 解决方案
> 1. **完善依赖项**：将用到的状态或属性填入 `deps`，触发 Effect 重新执行以捕获新闭包。
> 2. **函数式更新**：使用 `setState(prev => prev + 1)`，直接从 React 内部获取最新状态，无需依赖外部闭包。
> 3. **使用 `useRef`**：将最新状态存入 `ref.current`。由于 `ref` 的引用在全生命周期保持不变，在任何闭包中都能读取到最新修改的值。

> 
> ---
> 
> ### 【当前任务：Node.js Cluster 模块原理】
> 
> > **核心结论**：Node.js 的 `cluster` 模块是通过 **`child_process.fork()`** 启动多个子进程来实现多核 CPU 利用的。每个子进程都是一个独立的进程，拥有**自己独立的事件循环（Event Loop）和内存空间**。
> 
> #### 1. 核心工作机制
> * **主进程（Master/Primary）**：不负责处理具体的业务逻辑，而是专门负责**路由分发**和**子进程管理**（如监控子进程状态、自动重启等）。
> * **工作进程（Worker）**：由主进程 fork 出来，各自独立运行。它们共享同一个 TCP 服务器端口，但互不干扰。
> 
> #### 2. 请求分发策略（负载均衡）
> Node.js 默认提供了两种分发请求的模式：
> * **Round-Robin（轮询模式）**：除 Windows 外的默认模式。主进程监听端口，接收到连接后，通过时间片轮转（Round-Robin）的方式均匀地分发给各个子进程。
> * **Shared Socket（共享套接字模式）**：主进程创建监听 socket，然后直接发送给感兴趣的子进程，由子进程自行抢占连接。这种模式在高并发下可能导致负载不均（“惊群效应”）。
> 
> #### 3. 进程间通信（IPC）
> 由于子进程间**内存隔离**，它们无法直接共享状态（如 session 或全局变量）。进程间必须通过内建的 **IPC（Inter-Process Communication）** 通道，利用 `process.send()` 和 `process.on('message')` 进行状态同步，或者依赖外部媒介（如 Redis）来实现状态共享。
>
