## [16:34] 模式：验证

**问题**: Node.js 的 process.nextTick 和 setImmediate 的核心区别是什么？请简短回答

**Gemini 回复**:
> Gemini 说
> 
> Node.js 中 process.nextTick 和 setImmediate 的核心区别在于它们在事件循环（Event Loop）中的执行时机不同：
> 
> process.nextTick（当前阶段结束时执行）：
> 它的名字有点误导。它其实是“马上、立即”执行。它不属于事件循环的任何一个特定阶段，而是属于微任务队列（Microtask Queue）。一旦当前正在执行的代码（当前阶段）完成，在事件循环继续往下走之前，NextTick 队列里的回调会全部被清空。
> 
> setImmediate（下一次循环开始时执行）：
> 它的意思是“在事件循环的下一个阶段执行”。它专门在事件循环的 Check（检查）阶段 运行。这意味着它必须排队，等到当前的事件循环阶段走完，轮到 Check 阶段时才会执行。
> 
> 一句话总结
> 
> process.nextTick 比 setImmediate 执行得更早、更快。 process.nextTick 是“插队”到当前阶段的尾部，而 setImmediate 是乖乖排队到下一个专门的阶段。

**问题**: Node.js 中 cluster 模块和 worker_threads 的核心区别是什么？什么场景用哪个？

**Gemini 回复**:
> Gemini 说
> 
> 简单来说，这两者的核心区别在于内存共享机制。这也是决定你在什么场景下使用它们的根本原因：
> 
> cluster 模块：创建的是多个完全独立的独立进程（Processes）。每个进程都有自己独立的内存空间（不共享内存），它们通过主进程分发网络请求，最适合用来压榨多核 CPU 的性能来处理高并发的网络服务。
> 
> worker_threads 模块：创建的是单进程下的多线程（Threads）。所有的线程共享同一个进程的内存空间（可以通过 SharedArrayBuffer 高效传递数据），最适合用来处理耗时的密集计算，而不会阻塞主线程的异步事件循环。
> 
> 核心区别对比
> 特性	cluster (多进程)	worker_threads (多线程)
> 内存空间	完全隔离。每个进程都有独立的 V8 实例和内存。	共享内存。线程间可以直接操作同一块内存数据。
> 通信成本	高。需要通过进程间通信（IPC）进行序列化和反序列化。	极低。可以通过指针直接共享数据，几乎无开销。
> 主要解决问题	单个 Node.js 进程只能用单核，用来利用多核 CPU 处理更多网络连接。	单线程遇到重度计算会卡死，用来解放主线程的事件循环。
> 崩溃影响	一个工作进程崩溃不影响其他进程，系统容错率高。	一个线程发生致命错误可能导致整个进程崩溃。
> 端口共享	可以。多个工作进程可以共同监听同一个网络端口。	不可以。通常无法直接让多个线程共享监听同一个端口。
> 什么时候用哪个？（场景决策）
> 💡 选用 cluster 的场景：搭建高并发 Web 服务器
> 
> Node.js 默认是单进程的，这意味着它只能利用 CPU 的一个核心。如果你的服务器有 8 核，只跑一个普通的 Node.js 应用就浪费了其余 7 核。
> 
> 典型场景：Express / Koa / NestJS 编写的 API 网关、Web 应用。
> 
> 做法：通过 cluster 根据 CPU 核心数 fork 出对应数量的子进程。当大量 HTTP 请求涌入时，主进程会通过负载均衡（默认是 Round-Robin 轮询）把连接分发给各个子进程，极大提升了服务器的吞吐量。
> 
> 行业现状：在实际生产中，大家现在更倾向于使用 PM2 的 cluster 模式或者在 Docker/K8s 容器层面做横向扩展，直接手写 cluster 模块的情况变少了，但底层逻辑是一样的。
> 
> 💡 选用 worker_threads 的场景：处理 CPU 密集型任务
> 
> Node.js 的非阻塞 I/O 非常快，但如果让它做复杂的数学计算，主线程就会被死死卡住，导致期间所有的网络请求都无法响应。
> 
> 典型场景：大文件加解密（Crypto）、视频/图片压缩、复杂的 JSON 大数据解析、AI 矩阵运算或生成大量的 PDF 报表。
> 
> 做法：把这些耗时的计算任务丢给 worker_threads 异步执行。主线程继续高高兴兴地接收网络请求，等线程算完了把结果传回来即可。
> 
> 一句话总结
> 
> 如果你想让 Web 服务器并发量更高、充分利用多核，选 cluster（或者直接用 PM2）；如果你写代码时发现某段计算逻辑太耗时、把网页/接口卡死了，选 worker_threads。

## [17:23] 模式：通用

**问题**: JWT 认证的工作原理是什么？请简短回答

**Gemini 回复**:
> Gemini 说
> 
> JWT（JSON Web Token）认证是一种无状态的身份验证机制。简单来说，它的核心逻辑是：服务器不保存会话数据，而是把用户信息加密签名后做成一个“令牌”（Token）给客户端，客户端此后每次请求都带着这个令牌来证明身份。
> 
> 它的核心工作流程可以分为以下 4 个步骤：
> 
> 登录：用户在前端输入账号密码发送给服务器。
> 
> 生成：服务器验证成功后，将用户的 ID、角色等信息打包成一个 JSON 对象，并用只有服务器知道的密钥对其进行数字签名，生成一个 JWT 字符串发回给前端。
> 
> 存储与发送：前端收到 JWT 后，通常把它存进 localStorage 或 Cookie 中。之后每次向服务器请求数据时，都会在 HTTP 请求头（Header）的 Authorization 字段里带上这个 JWT。
> 
> 验证：服务器收到请求后，不需要查数据库或 Session，而是直接用手中的密钥去解密和验证这个 JWT 的签名。如果签名正确且没有过期，服务器就认为该请求合法，直接返回数据。
> 
> 核心优势：因为服务器不需要存 Session，所以非常适合分布式和微服务架构，横向扩展非常方便。
